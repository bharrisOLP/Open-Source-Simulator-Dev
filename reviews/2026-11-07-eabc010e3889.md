## Findings

No blocker and no major finding. All 7 claims hold. Two minor findings and two nits.

1. **minor: one per_worker decision for all BLAS libraries; a process-wide BLAS in the per-worker branch can stay
   at 1 thread.** `meow_gpu/src/meow_gpu/fde/eigensolver.py:714-718` (`_blas_limit`) and `:740-744`
   (`_host_map`). `per_worker` is True when any BLAS library has a layer outside `_SERIAL_LAYERS`. Then a
   process-wide library in the same process also gets its limit in each worker. Examples: a pthreads OpenBLAS
   (the numpy wheel) together with an MKL or OpenBLAS-OpenMP library of another package; an OpenBLAS with the
   layer "unknown"; OpenMP on Windows (process-wide, threadpoolctl 3.8.0 METADATA "Known Limitations"). For such a
   library, threadpoolctl 3.8.0 lets only the "controlling thread" set the count; the set of the other workers does
   nothing, they save the limited count 1 as their "original", and the last restore sets 1. Evidence
   (`/tmp/rv_meow6_blas.py`, the real pthreads OpenBLAS, the per-worker branch forced with `_SERIAL_LAYERS = ()`,
   8 `eigvals` of 72 x 72 per call): after call 6 the BLAS of the process stayed at [1, 1] (from [4, 4]). The
   default environment is not affected: `.venv-rocm` has two `libscipy_openblas` with "pthreads", so
   `per_worker` is False (also with jax, meow and tidy3d imported). Two more points: (a) the thread-local setters
   (`MKL_Set_Num_Threads_Local`; `omp_set_num_threads` for OpenBLAS-OpenMP) and the controlling-thread rule are
   those of threadpoolctl 3.8.0 (uv.lock: released 2026-11-05), but `meow_gpu/pyproject.toml:11` allows
   `threadpoolctl>=3.1`; the reviewer did not check the setters of the earlier releases. (b) For an OpenMP BLAS,
   the short cut `all(num_threads == 1)` (`:715`) reads the count of the calling thread only: a limit of 1 that
   the user set in the main thread does not reach the workers, and then no worker limit is set. Effect: speed only
   (the results do not change). Fix: decide for each library (for example `limits={prefix or filepath: 1}`):
   limit the process-wide libraries (pthreads, disabled, sequential, unknown, and all on Windows) in the caller
   under `_HOST_LOCK`, and the thread-local libraries in each worker; raise the floor to `threadpoolctl>=3.8` or
   say in the docstring that the per-worker semantics need 3.8.

2. **minor: the warm-start test does not detect a looser warm stop, and the admission parameter adds no coverage
   there.** `meow_gpu/tests/test_refine.py:371-391` (`test_warm_start_on_the_example_grid`). Evidence
   (`/tmp/rv_meow6_warm.py`, the same steps as the test, `meow_backend.REFINE_SWITCH_TOL` changed for the warm
   solve only): with the warm stop at 1e-3, 1e-2, 3e-2 and 1e-1, admission on and off, all 8 warm solves used
   `polish_used == "refine+davidson"` (the fallback), all gave the 4 neff of the double solve (max |dneff| 1.8e-14
   to 8.2e-14), and the test conditions held in each case. Admission on and off gave the same iterations (45, 43,
   47, 41). So the test guards the fallback on the warm path (a refinement that converges to a wrong pair, or a
   broken fallback). It does not guard the 1e-3 stop or the admission rule. The docstring says "each one through
   the fallback", but "keeps the warm path under test, with and without the admission rule" says more than the
   test does. Fix: say in the docstring that this case runs through the fallback and that a stop up to 1e-1 gives
   the same result; if the path must stay the same, assert `s.last_info.polish_used`.

3. **nit: README text after the new test.** `meow_gpu/README.md:541-544` (Limits) still says that the warm-start
