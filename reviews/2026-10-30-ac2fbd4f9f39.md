## Findings

No blocker and no major finding. Every number in the patch agrees with its JSON row or package README. Six minor
findings: caveats that the package READMEs give and the summaries drop, one wrong path, and one wording issue.

1. **minor** - STATUS.md:47 (bands). "triangular air holes 128 x 128: 5.6 s on the GPU against 89 s on 16 CPU
   threads". Evidence: `benchmarks/2026-10-30/bands-oblique.jsonl` row 2 (cpu:0) has `all_converged: false` and
   65.4 iterations per k point (GPU 54.4, all converged). `bands_gpu/README.md` says that the ratio of the times
   (15.8x) "compares unequal work" and gives 13x per iteration. STATUS gives the two times without this caveat, so a
   reader gets 16x. Fix: add "(the CPU run did not converge all k points; 13x per iteration)".
2. **minor** - STATUS.md:46-47 (bands). "TE at second order also in sheared voxels". Evidence: the order test of
   `bands_gpu/README.md` covers n = 64 to 128 only (error ratio 4.8). The "Known limits" of the same README say that
   above n = 128 the TE error falls slowly (2.98e-4 at 128, 2.04e-4 at 192: ratio 1.46 for a 1.5x finer grid, about
   first order), cause not known. Fix: "(TE at about second order from n = 64 to 128 in sheared voxels; slower above
   128)".
3. **minor** - STATUS.md:58-60 (thermal). The sentence attaches "mid-length rise equal to 2-D to 7e-6" and "the
   phase integral 1.0001" to the 11 M-cell run. Evidence: these values come from the 100 nm and 50 nm grids
   (`thermal_gpu/README.md`, 3-D heater table at 2.7 M cells). The reviewer ran the same comparison on the Mac CPU
   (float64): 100 nm 7.22e-6, integral 1.00012; 50 nm 7.14e-6, integral 1.00012. At 25 nm (11 M cells)
   `thermal3d.jsonl` row 3 gives (20.380446 - 20.380281) / 20.380 = 8.1e-6; the integral at 25 nm is not logged.
   Fix: "mid-length rise equal to 2-D to 7e-6 at 50 nm (8e-6 at 25 nm), ... the phase integral 1.0001 of 2-D (50 nm)",
   or "to 1e-5".
4. **minor** - STATUS.md:83 (charge). "No GPU gain at 73k cells (1.6x at 293k cells)". Evidence:
   `charge_gpu/README.md` (example section and "Known limits") compares the GPU with the **Mac CPU** (8.6 s against
   5.27 s in `charge-rc.jsonl`), and the 1.6x is for the charge part only (the mode part is slower on the GPU: 1.5 s
   against 1.0 s). All other speed lines of STATUS (lines 44, 47, 59, 89) compare with the 16 CPU threads of the GPU
   computer, so a reader assumes the same reference here. Fix: "(charge part, against the Mac CPU)".
5. **minor** - STATUS.md:81. The path `charge_gpu/rc.py` does not exist. The file is
   `charge_gpu/src/charge_gpu/rc.py` (STATUS line 86 gives the full form for `multigrid.py`). Fix the path.
6. **minor** - README.md:15 (thermal row). "3-D 11 million cells in 1.0 s (33x 16 CPU threads)". The 1.0 s and the
   33x are the CG time after compilation (`cg_s` 1.027 s against 34.021 s). The GPU setup adds 0.95 s (CPU 1.58 s),
   so the time with setup is 2.0 s against 35.6 s (18x); the first solve takes 3.5 s. The 2-D value of the same row
   uses the same CG-time rule, so the row is consistent with itself, but the summary does not name the rule. The 3-D
   solver is steady state only, while the Physics column says "2-D and 3-D". "33x 16 CPU threads" reads as a product.
   Fix: "3-D steady: 11 million cells, CG 1.0 s (33x faster than 16 CPU threads)".
