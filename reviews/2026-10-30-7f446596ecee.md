## Findings

The code of the batched solver is correct in every case that the reviewer tried (see below). The two major
findings are documentation numbers and claims that the data of this change does not support.

1. **major**: the 3-D FDTD number 0.9957 has no support in the data. Files: `meow_gpu/README.md:123` and
   `meow_gpu/src/meow_gpu/meow_backend.py:13`. The change replaces 0.9945 with 0.9957. The current row for this
   taper (20 nm grid, 100 segments) is `benchmarks/2026-10-30/fdtd-v3.jsonl` line 4, with `"T00": 0.99614`. The
   table of `suite/README.md:67` also gives 0.9961. No row in `benchmarks/` has 0.9957. The old value 0.9945 is the
   earlier row in `fdtd.jsonl`, which `fdtd-v3.jsonl` replaces. The 0.9957 comes from `suite/README.md:90,92`, a
   sentence that disagrees with its own table at line 67.
   Fix: write 0.9961 in both places and cite `benchmarks/2026-10-30/fdtd-v3.jsonl`. Follow-up outside this patch:
   `suite/README.md:90,92` and `docs/upstream-issues.md:15` also have 0.9957.

2. **major**: some speed claims disagree with the GPU rows of this change.
   - `meow_gpu/src/meow_gpu/meow_backend.py:20-21` says: "Small cross-sections do not fill the GPU, so B solves
     together cost much less than B solves one after the other". The rows show 1.16x to 1.23x in single precision
     (5.53 s against 4.75, 4.49 and 4.57 s). In mixed precision they show no gain (19.45 s against 18.27, 20.75 and
     18.75 s).
   - `meow_gpu/README.md:129-131` says that the fixed cost per iteration "dominates" and that the batched solve
     "shares this cost between B cells; its GPU speed-up is not measured yet". The table at lines 87-93 of the same
     README measures this speed-up. Line 96 of the README then says that "the fixed cost per iteration is not the
     largest cost here". These two statements disagree.
   Fix: in the module docstring, give the measured result (about 1.2x in single, none in mixed, RX 7900 XT,
   30-cell taper). Rewrite the "Known limits" bullet to match line 96 and the table.

3. **minor**: the explanation at `meow_gpu/README.md:96-97` does not fit the single-precision rows. It names the
   complex128 polish and the cold first batch as the "probable larger costs". Single precision has no polish. The
   rows give about 11.5 ms for each per-cell iteration (5.53 s / 480 iterations). They give about 43 ms for each
   B = 8 batch iteration (4.49 s / 105). So the cost of one batch iteration grows about 3.7x for 8x more members:
   work that grows with each member is the largest cost.
   Note: `modes_s` includes meow's post-processing. On the Mac CPU this was 0.64 s of about 7.8 s, so it does not
   change the conclusion.
   Fix: give these numbers, and say that the cause is not profiled yet.

4. **minor**: the GPU table has a wrong label for B = 16. In `meow_gpu/README.md:93` the label is "B = 16", but
   `compute_modes_gpu_batch` used 15 members (runs = ceil(30/16) = 2, width = ceil(30/2) = 15). The CPU table at
   line 107 correctly says "(15 used)". The rows in `eme-batch.jsonl` also record `"batch": 16`
   (`bench_eme_batch.py:79` writes the requested size, not the size that was used).
   Fix: change the label to "B = 16 (15 used)". Record the batch size that was used in the row.

5. **minor**: the GPU table gives max |dneff| = "0" for mixed precision (`meow_gpu/README.md:91-93`). The rows give
   5.9e-12, 6.3e-12 and 4.9e-12. Fix: write these values, or "< 1e-11".

6. **minor**: the CPU reference table (`meow_gpu/README.md:103-107`) has no row in `benchmarks/`. The reviewer ran
   the benchmark again on the same Mac CPU (`--precision single --repeat 1`):
   - These values are the same as in the table: iterations 477 / 170 / 101 / 68, the mean member iterations
     17.7 / 21.1 / 29.3, |S21| 0.9933414 / 0.9933439 / 0.9933439 / 0.9933448, and max |dneff| 3.4e-6 / 4.8e-6 /
     4.8e-6.
   - The times were 7.8 / 8.8 / 10.5 / 13.9 s, against 7.9 / 9.1 / 11.6 / 15.1 s in the table.
   - The per-cell value "15.9 mean iterations" is 477/30, so it includes the cold first cell. The JSON field
     `mean_iterations` (`bench_eme_batch.py:84`) does not include that cell (14.93 on the CPU, 15.03 in the GPU row).
     The batch field `mean_member_iterations` includes the cold first batch and the padded members.
   Fix: add the CPU rows to `benchmarks/`. Calculate the per-cell mean in the script as the README defines it.

7. **minor**: some paths of the change have no test. The reviewer tried each of them by hand, and each one gave
   correct results:
   - `test_batch.py:67` does not check the iterations in single precision on all devices. On the CPU, the
     iterations and matvecs of the batched solve are exactly those of the per-cell solve in all three precisions
     (single: 46/52/46 for both solves). Only the GPU needs the skip.
   - No test stops a member by the stall rule. The reviewer ran `davidson_batch` in single precision with a
     tolerance of 1e-9 for two members and 1e-5 for one member. The two members stalled at iterations 70 and 73,
     and the third member converged at iteration 58. These are the same iterations as `davidson`, with the same
     values.
   - No test sends several grid shapes, or an unsupported (bend) cell, to `compute_modes_gpu_batch`. The reviewer
     ran a list with two grid shapes and one bend cell. The output order was correct, and the tidy3d fallback ran.
     The maximum |dneff| against the per-cell solve was 4e-12.
   Fix: on the CPU, run the iteration check also in single precision. Add a stall test and a test with mixed
   grid shapes and a fallback cell.

8. **minor** (nit): the batched solve counts matvecs differently from `davidson` at the iteration limit.
   - At the limit, `davidson` also expands the subspace in its last iteration and counts those matvecs.
     `_davidson_batch_fixed` stops before that step (`eigensolver.py:485`). With max_iter = 5 the counts were 48
     (batch) and 56 (per-cell). The values were identical. So `SolveInfo.matvecs` is not "the per-cell result" in
     this case.
   - The comment at `eigensolver.py:308` says that the buffers of a stopped member "do not change". But
     `eigensolver.py:506` writes zero rows into these buffers at `min(m, M - b)`. This has no effect, because the
     result of the member is already saved.
   - In `compute_modes_gpu_batch`, the bend fallback warning points into `meow_backend.py`, not into the code of
     the caller.
   Fix: correct the comment. Optionally, document the matvec difference.

## What the reviewer tried to break

- **The patch is the working tree.** `git apply -R --check` of the patch on the working tree succeeds, so the
  files that the reviewer tested are the files of the patch. `tools/hygiene.py` passes on the 7 files. The reviewer
  found no host names, IP addresses, private paths, e-mail addresses, or client or PDK data. "Apple M5 Pro" and
  "rocm:0" are generic names.
- **Tests on the Mac CPU.** `uv run pytest -q` in `meow_gpu/` gives 29 passed in 22.7 s. The reviewer could not
  check the GPU claims (the 29 tests on the GPU, the 1.4e-3 field difference in single precision).
- **The batched solver against `_davidson_fixed`, line by line:**
  - The tolerance check and the stall rule (`better` and `stalled`, the same as the if/elif of the per-cell code).
  - The stop at the iteration limit: the result is the Ritz pairs of iteration max_iter, the same as per-cell.
  - The SVQB "kept == 0" break, and the restart when `m + b > M`.
  - The h-matrix update after the inserts, and the CGS2 projection.
  - In the mixed mode: the switch tolerance, "no iterations left" (the member keeps the complex64 values), the
    polish with a subspace of 3b, and the sums of iterations and matvecs.
  - Members that stopped: x = 0 and rn = NaN. These are masked: `rn[done] = inf`, `_expand_b` sets their rows to
    zero, and SVQB gives zero coefficients. Under vmap, a NaN cannot go into another member.
  - `donate_argnums` on v and w: no array is used after its donation.
  - `max_iter = 0`: the result is the initial block, the same as `davidson`.
  - Result: no defect.
- **Same steps, same results (on the CPU):**
  - In double, mixed and single precision, the iterations and matvecs of `solve_batch` are exactly those of
    `solve` for the 3 test members.
  - The stall stop in single precision with tol 1e-9 gives the same iterations (70, 73) and the same values.
  - At an iteration limit of 5, the values are identical. The matvec count differs (finding 8).
- **`compute_modes_gpu_batch` edge cases:**
  - Two grid shapes, mixed with each other, and one bend cell: the order is correct, the fallback runs, and
    max |dneff| is 4e-12.
  - num_pml (0, 0) and (5, 5) in one batch: the operators stack, and the results equal the per-cell solve.
  - One cell with batch 8, and an empty list: correct.
  - The warm start from the per-cell memory (`solve`, then a batch, in mixed precision): correct results.
  - max_iter = 3: a warning for each member that did not converge, and the same empty mode lists as the per-cell
    solve.
  - The run order: for each n and B, `pos = i * runs + j` covers each cell once, and the padded members solve
    cell n - 1.
- **The refactor of `solve`:** the target, the tolerance with the complex64 floor and the cap warning, the
  convergence rule with SINGLE_FLOOR, and the direction rule (`_orient`) are unchanged. The stacklevel of the
  floor warning still points at the caller of `solve`. `fields` uses `...` broadcasting, so `jax.vmap(fields)` is
  correct.
- **The numbers in the README against the rows:**
  - The GPU times and the max |dneff| in single precision match the rows.
  - 1.2x = 5.53 / 4.49. "2.8x to 7x fewer iterations" = 477/170 and 477/68. "About 46 cold iterations" matches the
    rows.
  - The polish claim (about 40 iterations from converged vectors, 0.45 um strip, 40 nm) is correct: the reviewer
    measured 40 (90 for a cold start).
  - The FDTD value, the "0" entries, the B = 16 label and the speed claims are wrong (findings 1, 2, 4 and 5).
- **The physics.** The batched path uses the same operator, the same preconditioner (with eps_ref for each member)
  and the same tidy3d direction rule. `test_batch_follows_the_tidy3d_direction_rule` checks the S21 below cutoff
  against tidy3d (3e-6). The reviewer found no change in the physics.

The scratch scripts of the reviewer are in a temporary folder, not in the repository.
