## Findings

How the reviewer checked: the fdtdx 0.6.3 wheel is in the local uv cache. The reviewer read its source
(`objects/static_material/polygon.py`, `fdtd/initialization.py`, `core/grid.py`) and ran the adapter on the Mac CPU
with `uv run --offline --with fdtdx==0.6.3` (an overlay environment; it resolved JAX 0.12.0.1, not the 0.11.1 of the
GPU computer). The probe scripts are in the session scratchpad, not in the repository.

fdtdx 0.6.3 facts that the findings use:
- `ExtrudedPolygon.__post_init__` sets the real size of the two transverse axes to the vertex bounding box, and it
  raises if the caller gives a different size. So the adapter cannot set the object size.
- `get_voxel_mask_for_shape` adds `0.5 * real_shape` to the vertices. So the lower corner of the vertex bounding box
  is always at the lower grid edge of the object, and the mask is sampled at `(i + 0.5) * step` in that frame.
- On a uniform grid, the cell count is `round(length / step)` (nearest).
- `RectilinearGrid.bounds_for_anchor` picks the lower edge, among the positions that fit in the volume, whose anchor
  is nearest to the requested one. An object that does not fit is moved, with no warning.

1. **major** - `suite/src/photonsuite/fdtd.py:108-116`: the Polygon path does not put the polygon at its true
   position, and its upper (right, top) edges are not on the shared grid edges. The adapter snaps the lower corner
   of the bounding box to `cell(bx0)`, `cell(by0)`, and fdtdx puts the polygon bounding box exactly there. So the
   whole polygon moves by `cell(bx0) - bx0` (up to half a cell on each axis), and its right and top edges fall on
   `round(cell(bx0) + w)`, not on `cell(bx0 + w)` like a Rect. This is the "position and size rounded separately"
   error that this change fixes for segments and Rects (fdtd.py:95-97 says that the shared edges are fixed). Evidence
   (fdtdx 0.6.3, CPU, 40 nm grid, window (-1.2, 1.2) x (-0.8, 1.0)):
   - A rectangle Polygon from x = -0.264 to 0.232 fills columns 33 to 44. The Rect of the same corners fills
     columns 33 to 45. The claim "a rectangle Polygon places the same inverse permittivity as the Rect" is true only
     for corners on grid edges; the test uses only such corners (x -0.24 / 0.24 = cells 34 / 46, y 0 / 0.2 = cells
     30 / 35, `suite/tests/test_fdtd.py:39-40`).
   - A Polygon [-0.25, 0.232) then a Rect [0.232, 0.6) leave one column of oxide between them (column 45). Two
     Rects on the same edges leave no gap. A Polygon with its top at y = 0.232 and a Rect on top leave one row of
     oxide (row 35).
   - The 80 degree polygons of `suite/bench/sloped_taper.py`, sampled in the same way: 90 of 100 segments at 25 nm
     and 100 of 100 at 20 nm give a mask that is not mirror-symmetric about x = 0 (one sidewall column of 9 to 11
     cells moves to the other side; the centroid moves by up to 12.5 nm at 25 nm and 9 nm at 20 nm). The Rect taper
     stays symmetric. So the sloped FDTD rows in `fdtd-v2.jsonl` contain a lateral jitter of the guide from segment
     to segment that the vertical-wall rows do not have. Its effect on T00 is not measured; a rough estimate is up to
     about 0.1 %, which is the size of the sloped-minus-vertical difference that the docs report.
   - `suite/README.md:54` ("a binary mask at the cell centers") is true only in the moved frame.

   Fix: sample the polygon at the true cell centers, with the rule of `Polygon.contains`. For example, compute the
   mask with `shapely.contains_xy` on the cells `[cell(bx0), cell(bx1)) x [cell(by0), cell(by1))` and give it to
   fdtdx as `UniformMaterialObject` boxes (one box for each run of equal columns), or as an `ExtrudedPolygon` of the
   staircase outline (all its vertices are on grid edges, so its bounding box is a whole number of cells and the fdtdx
   frame is the true frame). Add tests with corners off the grid: a rectangle Polygon equals the Rect for random
   corners; a Polygon and a Rect that share an edge leave no gap; a symmetric polygon gives a symmetric mask. Then run
   the sloped rows again, and change the numbers in the docs.

2. **major** - `suite/src/photonsuite/fdtd.py:108` with `fdtd.py:168` and `fdtd.py:193-194`: fdtdx moves a Polygon
   by one cell, with no error, when its rounded size does not fit in the volume. The clip box is the window plus the
   PML, but the volume is that length rounded to whole cells (fdtd.py:168). So a polygon that leaves the window can
   end past the volume after the lower-corner snap and the size rounding, and `bounds_for_anchor` then moves it down
   (or left) by one cell. Evidence: y range (-0.8, 1.01) at 25 nm (2.31 um = 92.4 cells, the volume has 92 rows); a
   Polygon from y = 0.22 to 5.0 fills rows 50 to 91; the Rect of the same corners fills rows 51 to 91. The lower
   edge of the polygon (inside the window, the edge that matters) is 25 nm too low. The same happens at exact
   half-cell ties, because `cell()` rounds half up and fdtdx rounds half to even. Fix: clip to the rounded volume
   (origin + n_cells * step), and after `place_objects` check that the slice of each shape object is the slice that
   the adapter asked for (raise if not). The fix of finding 1 also removes the size rounding.

3. **minor** - `suite/src/photonsuite/fdtd.py:109-116`: a Polygon part that is narrower than half a cell on one
   axis (a thin wall, or a shape that enters the window plus the PML by less than half a cell) makes fdtdx fail
   ("Interval size must be positive, got 0"). A Rect of the same size is skipped (`fdtd.py:103-104`). Evidence: a
   15 nm wide Polygon at 40 nm, and a Polygon from x = 1.59 to 3.0 (10 nm inside the clip box), both raise
   ValueError; the same Rects place. Fix: skip a part when its cell range is empty on an axis, as for a Rect.

4. **minor** - `suite/src/photonsuite/fdtd.py:131-132`: the comment says that a segment of at least one step always
   gets at least one cell. This is false in floating point. Example: step 0.02, a segment from z = 3.79 to 3.81

   name the cause. The reviewer found 428 such cases in a scan of segments of exactly one step at half-cell
   positions. Fix: in `_setup`, after the snap, raise the same clear ValueError when `iz1 <= iz0`.

5. **minor** - `suite/README.md:95` ("both methods see the same small decrease (0.1 % and 0.03 %)") and

## What the reviewer tried to break

- **Tests on the Mac.** `cd suite && uv run pytest -q`: 12 passed, 1 skipped (test_fdtd.py, no fdtdx). With the
  fdtdx 0.6.3 overlay: `tests/test_fdtd.py` 4 passed, 1 skipped (the GPU test); this includes the straight guide on
  the CPU (so the CPU fallback of `_device()` works) and the gap regression test.
- **fdtdx semantics (source read).** `ExtrudedPolygon` with `axis=0`: `get_transverse_axes(0) = (1, 2)`, so vertex
  x goes to fdtdx axis 1 and vertex y to axis 2, as the adapter expects. The vertices must be centered at the bounding
  box center (the adapter does this, `fdtd.py:113`), but see findings 1 and 2 for the frame.
- **Vertex centering and margins.** Correct when the bounding box is on grid edges; moved by up to half a cell when it
  is not (finding 1); moved by one more cell when it does not fit (finding 2).
- **MultiPolygon.** An arch clipped at the top of the window gives two parts, two objects (`seg0_shape0_0`,
  `seg0_shape0_1`) and the expected 700 Si cells. Points and lines from the clip are filtered (`geom_type`, area).
- **Holes.** `Polygon.__post_init__` accepts only valid simple polygons (no interiors). The intersection of a simply
  connected polygon with a box has no holes, so `exterior.coords` loses nothing.
- **Vertex orientation.** fdtdx uses `matplotlib.path.Path.contains_points`; the orientation from shapely does not
  change the mask (the rectangle and arch probes give the expected cells).
- **Fill order.** fdtdx sorts the static material objects by `placement_order` with a stable sort, and Rect boxes and
  ExtrudedPolygons are in the same list. Probe E (Rect Si slab, Polygon oxide trench, Polygon Si core) gives
  [Si, oxide, Si, oxide, Si, oxide] at x = -0.8, -0.35, 0, 0.35, 0.8, 1.1, as for three Rects.
- **Sub-pixel claim.** `ExtrudedPolygon` inherits the binary fallback of `get_fill_fraction_for_shape`; only the GDS
  layer stack has a fractional fill. The claim "no sub-pixel smoothing" is correct.
- **Segment snapping.** The z edges of the middle segments use the same `cell()` on both sides, so they share the
  grid edge. The volume rounding (`round(length / step)`) is the same as the rounding of fdtdx
  (`_resolve_grid_from_volume`). Zero-cell segments are possible in floating point (finding 4).
- **Numbers in the docs against `fdtd-v2.jsonl`.** All agree: straight T 0.9999995, 10.8 s, 3.3 M cells; taper
  0.9974 / 0.9981 / 0.9957 with T_flux 1.0017 / 1.0019 / 1.0009, 212 s; sloped 0.9965 / 0.9954 with T_flux 1.0011 /
  0.9998; EME 0.9878. The sloped EME uses the same window, 0.02 um mode grid, 10 modes and 0.2 um cells as
  `bench/eme_taper.py` (0.9888). "differ by 0.1 % at most" against `fdtd.jsonl`: the largest change is 0.12 %
  (0.99452 to 0.99568), acceptable as rounded. The geometry of the 80 degree bench is correct (inset 0.22 / tan 80
  degrees = 0.0388 um on each side).
- **Device change.** `_device()` falls back to the CPU on the Mac; `FDTDResult.device` is now a device string
  ("rocm:0"), and the only users (`bench/fdtd_taper.py`, `bench/fdtd_straight.py`) write it into a JSON key; nothing
  compares it with "gpu".
- **Private data.** `uv run --script tools/hygiene.py` on the staged files: exit 0. The reviewer saw no host names,
  private paths, client names or PDK values in the diff.
- **Not checked.** The GPU runs (no access to the GPU computer); the size of the effect of finding 1 on the sloped
  T00 values; the slowdown after an EME run and its cause.
