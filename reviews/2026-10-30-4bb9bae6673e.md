## Findings

1. **major** - The fallback alone can return `converged=True` with a wrong mode, and no test catches the wrong
   4th mode that this change claims to fix (`meow_gpu/tests/test_refine.py:214-244`,
   `meow_gpu/src/meow_gpu/fde/eigensolver.py:602-618`, `meow_gpu/README.md:172-181`).
   - Evidence (GPU, x64 on; reviewer script; `_track` patched to ignore `rn_vals`, which turns off only the
     admission rule): on the grid of the example (`sin_tip(dx=0.05)`, 4 modes, extra 8), the variant "fallback
     only" gives `converged=True`, residual 7.0e-12, `polish_used="refine+davidson"`, neff
     [1.44729625, 1.44709062, 1.44188095, **1.44122808**]. The new code and `polish="davidson"` give
     [... 1.44188095, **1.4418766**]. So the complex128 Davidson fallback, started from the refined block, does not
     find an eigenvalue that the refined block does not hold. It then returns a farther mode as converged (the
     failure class of the previous blocker). Only the admission rule prevents this here.
   - On the grid of the new test (`sin_tip()`, 100 nm), "fallback only" gives the same converged result as the new
     code (neff to 8 digits). "Admission only" does not converge (3.6e-10). So the regression test checks the
     fallback only. If the admission is lost in `refine` (for example `_track(vals, theta[:nb])` at
     eigensolver.py:496), all 87 tests except one `_track` unit assertion still pass, and the example returns a
     wrong 4th mode with `converged=True`.
   - The README sentence "so `mixed` converges where the earlier polish converges" (README.md:173; also
     eigensolver.py:605-606) hides this. The fallback starts from other vectors (the refined block, after a
     complex64 stop at 1e-3, not 2e-5) with fewer iterations (`rest`). It can converge to another mode set than the
     earlier polish.
   - Fix: (a) add an end-to-end regression case where the admission is necessary: the example grid
     (`sin_tip(dx=0.05)`, about 3.5 s per solve on the RX 7900 XT), with all 4 neff against `polish="davidson"` or
     the double solve, and the fields of the guided modes; or a smaller structure that shows the same effect.
     (b) Change the README and the docstring: the fallback converges where the refinement stalls, but it cannot
     bring in an eigenvalue that the refined block misses; the result is then the documented limit "all precisions
     can miss eigenvalues". (c) Optional, more robust: start the fallback from the refined k wanted vectors plus the
     complex64 block `lo.vectors` (the start of the earlier polish), not from the refined block only.

2. **minor** - With an out-of-reach tolerance, "mixed" now runs to `max_iter` and is about 10x slower, and the
   result can be worse than that of the refinement alone (`meow_gpu/src/meow_gpu/fde/eigensolver.py:613`; README.md:204
   and :356-357).
   - Evidence (GPU, strip of `test_refine.py`, `tol=1e-17`, default `max_iter=500`): before (no fallback) 53
     iterations, 56 complex128 applies, 0.38 s, residual 1.44e-14; now 500 iterations, 5424 complex128 applies,
     3.95 s, residual 3.86e-14 (`polish="davidson"`: 500 iterations, 3.78 s). The fallback calls
     `_davidson_fixed` with `stall_iters=0`, so the halving rule of the refinement is lost; `_davidson_fixed` gives
     the last step, not the best one. The test needed `max_iter=120` for this reason (test_refine.py:206). The README
     says that the refinement stops after 7 steps and that the fallback "finishes the solve"; it does not say that a
     tolerance below the complex128 floor now costs all remaining iterations.
   - Fix: give the fallback a stall rule (for example `stall_iters=12`; the rule acts only below `STALL_FLOOR`),
     and keep the refinement result when the fallback ends without convergence and with a larger residual. Or
     document the cost in the README limits.

3. **minor** - The batched fallback path has no test (`meow_gpu/src/meow_gpu/fde/eigensolver.py:913-929`,
   `BatchEigResult.polishes`, `meow_backend.py:214-216`).
   - Evidence: the reviewer ran it on the GPU: `solve_batch` of two strips with `tol=1e-17`, `max_iter=120` gives
     `polish_used="refine+davidson"`, 120 iterations and 968 / 864 complex128 applies per member; `solve_batch([sin_tip()])`
     gives "refine+davidson", converged, neff equal to `solve` to 4.7e-15. The code is correct, but no test checks it.
   - Fix: add an assertion on `last_batch_info[i].polish_used` and `iterations == max_iter` in one batch test.

4. **minor** (outside the patch; no action needed for this commit) - Without `jax_enable_x64`, "mixed" silently runs
   its "complex128" parts in complex64. In the first reviewer run (x64 off) all variants of the sin tip stopped at
   residuals of 8e-6 to 4e-4, and `polish="davidson"` reported `matvecs_hi=0`. Tests and benches enable x64, so the
   numbers of this change are valid. Suggestion for a ticket: `davidson` / `refine` raise an error when the
   precision needs complex128 and x64 is off.
