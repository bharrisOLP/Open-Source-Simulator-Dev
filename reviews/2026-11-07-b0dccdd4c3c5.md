## Findings

1. **major**: bands_gpu/src/bands_gpu/sampling.py:139-144 and bands_gpu/src/bands_gpu/geometry.py:301-308 (the
   fitted gradient and `norm > 0`); bands_gpu/README.md:375 (the known limit). A fitted gradient that is zero in
   exact arithmetic is a rounding residue. Its value (and so the voxel normal) depends on the summation order. Thus
   the NumPy and JAX paths give different tensors and different bands. This occurs for a common geometry, not only
   for "a thin feature centered in a voxel". Evidence (scratch script rv6_ties.py, on the GPU): the test geometry
   "two rods 0.01 apart" (32 x 32, sub 8) with silicon and oxide values (eps 3.48^2 in 1.444^2) gives a difference
   of 7.8e-2 in eps_inv in one voxel (NumPy: |n| = 1, a normal from rounding noise; JAX: |n| = 0, isotropic). The
   TE bands at X and M differ by **7.77e-4** between `sampling="numpy"` and `sampling="jax"` (TM 3e-16). A thin
   centered slab (1-D) gives 1.39e-1 (here NumPy is isotropic and JAX takes the tensor). A small centered sphere
   gives 6.5e-2 (GPU) and 5.7e-2 (CPU). The test cells hide this: the symmetric voxels of the tests have
   dyadic eps (12, 1, 12.25), so the moment sums are exact in every order. With the default `"auto"`, the result for
   one structure jumps at the 1e-3 level when the grid crosses 1e8 inside tests. The README claim "bands JAX vs NumPy
   below 1e-12" is true only for the test cells. Fix: in both paths, treat a fitted gradient whose norm is below a
   rounding bound as zero. An example of the bound: norm <= 1e-10 x max(eps) x max|coef|. Then the reference also
   stops taking a normal from rounding noise. Add a test with non-dyadic eps in symmetric voxels (the two Si rods, a
   small centered sphere, a thin centered slab) that asserts the same eps_inv and the same bands in both paths.
   Correct the known limit in the README.
2. **minor**: bands_gpu/src/bands_gpu/sampling.py:121 (one `lax.scan` per object, unrolled in the trace) and
   sampling.py:42 (AUTO_MIN_WORK). The compile time increases with the number of objects, but the "auto" rule counts
   only samples x images. Evidence (rv6_auto.py): a 10 x 10 supercell with 100 rods, 80 x 80, sub 8, has a work of
   3.7e8, so "auto" selects JAX. NumPy takes 1.374 s. The first JAX call takes 3.367 s (the second call takes
   0.045 s). With 36 rods at 144 x 144, NumPy takes 1.536 s and JAX first takes 1.198 s. The README value "first
   call 0.380 to 0.772 s" and the rationale of the threshold come from cells with 1 or 2 objects. Fix: add a term per
   object to the auto rule, or scan over the objects of one kind (with padded image lists). State the object
   dependence in the README.
3. **minor**: bands_gpu/README.md:73 ("at most 2^24 samples per slab") and sampling.py:22. The code at sampling.py:181
   (`step = max(1, ...)`) does not apply this limit when one voxel plane along the first used axis has more than
   `max_samples` samples. An example is a 3-D cell with a 256 x 256 cross-section at sub 8: 3.4e7 samples per plane.
   Fix: write "at most 2^24 samples, or one voxel plane", or split the plane along a second axis.
4. **minor**: bands_gpu/bench/bench_sampling.py:48-55. The times are rounded to 1 ms. Thus the speed-ups 16.0x,
   16.2x, 28.7x and 31.1x come from jax_s values of 0.003 to 0.008 s, with a rounding error of 6 to 17 %. The README
   table gives them with 3 digits. Fix: round to 0.1 ms or give the mean of several calls, or give fewer digits.
5. **minor**: bands_gpu/src/bands_gpu/sampling.py:47 (`supported`). This function checks for overrides of
   eps_inverse, voxel_averages and _sample, but not of `points`, `axes` or `unit_basis`. A subclass with other sample
   positions silently gets the JAX samples of Cell under "auto". Fix: add these methods to the list.
