## Findings

1. **minor** - `addon_gpu/suite_runner.py:104-106` (`TIMEOUT_EXITS`) and `:315` (`timed_out`); `addon_gpu/README.md:289-292`
   (the paragraph "The time limit of each module now uses GNU timeout"); `addon_gpu/tests/test_suite_runner.py:138-140`.
   The return code -9 does not mean only "the time limit".
   - Evidence (GPU computer, GNU coreutils timeout 9.7, return status read with perl `system`):
     `gnutimeout 10 sh -c 'kill -9 $$'` ends by signal 9 with no time-out. GNU timeout raises the signal of its
     child again on itself, so Python sees -9. The uutils timeout 0.8.0 does the same. `gnutimeout 1 sleep 5` gives
     124, and the time-out with `-k 1` and an ignored SIGTERM gives signal 9 (as the author says).
   - Effect: a module whose pytest process gets SIGKILL from another source (the OOM killer, or a kernel kill after
     a GPU fault) now gives `timed_out: true`. It counts in the `timeout` column of `--summary` and in
     `--stop-after-timeouts`. Before this patch, -9 was not in `TIMEOUT_EXITS`, so such a row had
     `timed_out: false`. This matters for the diagnosis of a crash (the kernel Oops of 2026-11-07). No logged number
     is wrong: each row keeps `exit` and `wall_s`, and all 120 new rows exit 0 or 1.
   - Fix: `timed_out = proc.returncode in TIMEOUT_EXITS and wall_s >= args.timeout`. Add a test where the command
     kills itself with SIGKILL before the limit (expect -9 and `timed_out` false). Say in the comment and in the
     README that -9 also comes from a SIGKILL of the module process before the limit.

2. **minor** - `addon_gpu/tests/test_patches.py:250-269` and `tools/env/addon_patches/README.md:91-93` ("No patch
   0005": "31 write a NaN value ...; the one module in both"). The count depends on the pattern, and the stated fact is not
   complete.
   - The pattern of the test knows only the words 0x7fc00000, 0xffc00000 and 0x7f800001. With a wider pattern (any
     word `0x7fc.....`, `0xffc.....`, `0x7f8.....`, `xp.nan`, `float32("nan")`), 35 modules write a NaN, and 2
     modules are in both sets: `meep_gpu/test_region_dispatch.py` imports `deposit_repair` and plants the NaN word
     `0x7FC5A5A5` (`SENTINEL`, its line 48).
   - That module is host NumPy only. It checks that the sentinel outside the cells of each form survives, and it
     compares no GPU NaN word of the repair. So the decision "no patch 0005" stays valid. Also, in the two logged
     whole-suite runs, no failure of the 79 modules that name the repair comes from the repair (the failing ones
     are certification records and the Triton version).
   - But the README gives the count as a fact, and the test asserts
     `names & plants == {"meep_gpu/test_triton_kernels.py"}`, which records the blind spot of the pattern.
   - Fix: widen the pattern (for example `0x7fc[0-9a-f]{5}|0xffc[0-9a-f]{5}|0x7f8[0-9a-f]{5}`, `xp.nan`,
     `float(32|64)("nan")`), name both modules with the reason why each one compares no GPU NaN word of the repair, and
     correct the counts in the README and in the docstring of the test.
