## Findings

1. **major** - the memory budget of `image_planes` is not true outside the one tested case.
   optics_gpu/src/optics_gpu/pop.py:521-531 (`_planes_step`), :544 and :546 (`_add_grouped`), :488 (docstring);
   optics_gpu/README.md:125-126 ("The memory of one chunk ... is at most `SUM_ELEMENTS` complex128 values (512 MB);
   the result E is outside that budget") and :159 ("at most the budget and E").
   Evidence (GPU computer, default chunk, peak `max_memory_allocated` minus the start, minus E, divided by
   16 x SUM_ELEMENTS bytes):
   - Z 21, 128 x 128, complex128: 0.88 (the tested case; the step rounds down to 9216 rays, so there is slack).
   - Z 41, 512 x 512, complex128: **1.30**; complex64: **1.13**.
   - Z 101, 512 x 512, complex128: **1.45** (step 425 < GROUP_RAYS).
   - Z 1000, 1 x 1 grid (an axial scan), complex64: **1.28**.
   Causes:
   - `torch.bmm(...).sum(0, dtype=complex128)` makes one more (Z Nx, Ny) complex128 tensor (the size of E) before
     `E +=`. The model of `_planes_step` does not count it.
   - If step < GROUP_RAYS (nb = 0), `u[:, n:] @ v[:, n:].T` makes a full (Z Nx, Ny) tensor, but the model counts
     only step / GROUP_RAYS of it (Z 101, 512^2: 26.5e6 values against 10.7e6 counted).
   - The weights `w` are made in float64/complex128 with about 2 to 3 (Z, chunk) temporaries for both dtypes; the
     model counts 2 nz x 0.5 for complex64. This dominates for a small grid with many planes.
   So the real bound is about budget + 2 E (plus the w temporaries), not budget + E.
   Fix: count the (Z Nx, Ny) complex128 output of the group sum (and the full (P, Q) output when step <
   GROUP_RAYS) and about 3 nz complex128 values per ray for `w` in `_planes_step`, or reduce the temporaries
   (for example `E.addmm_` / accumulate in place for complex128), or state the true bound in the docstring and
   README. Add a memory test without rounding slack (for example monkeypatch SUM_ELEMENTS smaller, Z 41).

2. **minor** - three speedup cells of the README table do not match the JSON rows.
   optics_gpu/README.md:248, :249, :252. The cells are quotients of the rounded times, not the `speedup_c64`
   fields: 27.9x (row: 27.99, so 28.0x), 26.7x (row: 26.64, so 26.6x), 26.9x (row: 26.84, so 26.8x). All other
   cells match.
   Fix: use the `speedup_c128` / `speedup_c64` fields of the rows.

3. **minor** - the complex64 accuracy figures are case-specific; cases under the guard give larger errors.
   optics_gpu/src/optics_gpu/pop.py:478-483 (docstring: "1.5e-6 for 1024"), optics_gpu/README.md:114-123,
   optics_gpu/tests/test_image_planes.py:43 and :121.
   Evidence (GPU, complex64 against complex128, all with the guard passed):
   - 2e5 identical rays (L' 0.5, M' 0.3), grid +-120 um (243 rad): field 3.6e-5 of the largest |E| (above the
     2e-5 field tolerance of the test and 24x the "1.5e-6" of the docstring); d eta with one power 3.4e-7.
   - a uniform pupil of NA 0.6 (7.1e4 rays), grid +-100 um at 0.5 um (243 rad): d eta with one power 3.3e-7
     (4x the "at most 8.3e-8 in the checks"); field 1.5e-6.
   - a tilted collimated beam (L0 0.55), grid +-110 um (254 rad): field 3.5e-6, d eta 1.2e-7 / 1.3e-7.
   All are below the 1e-6 eta bound of the test, and the README says "in the checks", so the text is not false.
   But the test "near PHASE32_MAX" (Gaussian focus) weights the rays at L' 0.6 by exp(-5.76) per axis, so the
   large grid phases carry almost no field.
   Fix: say that the figures are for the tested fields and that a coherent or wide-angle field gives up to about
   4e-5 (field) and 3e-7 (eta); add the uniform-pupil case to the complex64 test.

4. **minor** - unlogged development claims.
   optics_gpu/src/optics_gpu/pop.py:481 ("6.5e-6 of the largest |E| for groups of 4096 rays") and
   optics_gpu/README.md:118-119 ("Smaller groups were slower, larger groups less accurate, in development runs").
   No row, log or test supports them.
   Fix: log a small sweep of GROUP_RAYS (time and error) in benchmarks/, or remove the numbers.

5. **minor** - `_grid` flattens a 2-D input without an error.
