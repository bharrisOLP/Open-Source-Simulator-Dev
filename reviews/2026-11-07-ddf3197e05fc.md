## Findings

No blocker and no major finding. The defect and the fix reproduce exactly as claimed (see below).

1. **minor: README text that describes the code before the cold-start stop.** `meow_gpu/README.md:259` says "The
   complex64 Davidson stops at a residual of 1e-3 (`REFINE_SWITCH_TOL`)". This is now true only after a warm start
   (or for the low-level `davidson`). `meow_gpu/README.md:94-115`: the batched EME table (mixed column, B = 4 / 8 /
   16) and "the cold first batch (52 iterations in single, 49 in mixed precision)" come from the 2026-10-30 rows. With
   this change the cold first batch of mixed at B = 8 takes 72 iterations (`meow-cold-switch.jsonl` row 6,
   `iterations_max[0]`; 46 with `--switch-tol 1e-3`, row 8), and B = 16 (15 cold members at 2e-5) was not measured
   again. The rows are dated, so the text is not false, but a reader takes them as the current default. Fix: at
   line 259 add "after a warm start; after a cold start `COLD_SWITCH_TOL` (see "Cold starts")", and mark the mixed
   column of the batched table as "before the cold-start stop of 2026-11-07" (or measure B = 4 / 16 again).
2. **minor: the warm-start path (stop at 1e-3) on the near-degenerate tip has no test.** After the change,
   `test_example_grid_gives_the_modes_of_the_earlier_polish` (`meow_gpu/tests/test_refine.py:323`) exercises only the
   cold path (2e-5). The warm path keeps 1e-3, where the admission rule and the fallback are known not to be stable
   for this structure. My runs (1 BLAS thread at the start of the process, admission on and off): 14 warm starts of
   the 50 nm tip (from tips of side 0.25 / 0.28 / 0.32 / 0.35 / 0.5 um, from the end of a taper chain 0.6 -> 0.32 um,
   and from a core of index 1.9) all gave the 4 neff of the double solve (max |dneff| <= 1e-13). But each one used
   `polish_used == "refine+davidson"`: the refinement stalled and the fallback gave the result each time. So the
   risk is not reproduced, but each warm result depends on the fallback. Fix: add a cheap warm-start variant to
   `test_refine.py` (for example a warm start from side 0.28, about 1.5 s per solve, admission on and off), so that
   a later change of the fallback or the stall rule cannot break the warm path silently. README:531-534 (the new
   "Limits" item) already states the risk.
3. **minor: the cold-start rule is only in `GPUModeSolver`.** `meow_gpu/src/meow_gpu/fde/eigensolver.py:581` and
   `:928`: `davidson` and `davidson_batch` with a random block and `switch_tol=None` still stop at 1e-3 (the
   HEAD-equivalent cold run below gives the wrong pair through this path). The README names
   `fde.eigensolver.davidson_batch` as an API (`meow_gpu/README.md:32`). Also, `davidson_batch` now receives an array
   for `switch_tol` (it works: `np.maximum` at `:960` broadcasts it), but its annotation is `float | None` and its
   docstring says "as for davidson". Fix: in the two docstrings say that the default 1e-3 is for a warm block and
   that a random block should use `DAVIDSON_SWITCH_TOL` (or add a `cold` argument and move the rule down); annotate
   `switch_tol` of `davidson_batch` as a float or an array of B values.
4. **minor: scope of the BLAS limit.** `meow_gpu/src/meow_gpu/fde/eigensolver.py:684-701` (`_blas_limit`) says that
   threadpoolctl "changes the thread count of the BLAS for the whole process". That is true for OpenBLAS with the
   pthreads back end (the PyPI wheels of numpy 2.4.6 and scipy 1.18.1 in `.venv-rocm`). For an OpenMP back end
   (OpenBLAS-OpenMP or MKL builds, for example from conda) the setting is thread-local (threadpoolctl 3.8.0, METADATA
   "Known Limitations", issue 208): the limit set in the main thread does not reach the pool workers, and the pool
   oversubscribes again. `test_host_pool_keeps_one_blas_thread` would detect this on such a platform. Concurrency:
   two threads that call `_host_map` at the same time (two solvers in two user threads) can race (one can save the
   limited count 1 as its "original" and restore it, or one pool can run without the limit). A 5 s stress run with
   two threads ended with OpenBLAS at 4 threads (no lasting change seen). The post-processing thread of
   `compute_modes_gpu_batch` runs its BLAS with 1 thread while the limit holds (performance only; the full test run
   with this overlap passed). The no-threadpoolctl branch reads the variables at call time, so it cannot detect a
   variable set after numpy loaded (threadpoolctl is now a required dependency, so this branch is rare). Fix: if
   `_BLAS.info()` reports `threading_layer == "openmp"`, set the limit inside each worker (or run the items one after
   the other); state in the docstring that one caller at a time is assumed.
5. **minor: a broken line in a logged run.** `benchmarks/2026-11-07/meow-kernel-reduce.txt:78-79`: stray stderr text
   "(null): No such file or directory" splits the line "max rel diff 9.4e-07" (run without thread variables). The
   value is not cited in the README. Fix: add a note to the log (the source of the message is not known) or keep
   stderr out of the log in the next run.
6. **nit: test side effect.** `meow_gpu/tests/test_batch.py:281` (`test_host_pool_without_a_blas_limit`) sets
   `HOST_THREADS = 4`; if the module pool `_POOL` does not exist yet (the test runs alone or first), the pool is made
   with 4 workers and stays so for the rest of the process. Fix: `monkeypatch.setattr(E, "_POOL", None)` too.
7. **nit: diag tool docstring.** `meow_gpu/bench/diag_tip.py:1-9` says "at several BLAS thread counts
   (threadpoolctl)", but the README says that a thread count changed during the run gives the result of the count at
   the start. Fix: say in the docstring that a reproduction needs `OPENBLAS_NUM_THREADS=1` in the environment at the
   start of the process.
