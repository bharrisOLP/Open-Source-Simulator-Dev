## Findings

1. **major** - optics_gpu/README.md:79. The README says that the GPU is compared "against NumPy and PyTorch on
   the 16 CPU threads of the same computer". The evidence contradicts this. Each row of
   benchmarks/2026-10-30/optics-trace.jsonl has `"threads": 8` (torch.get_num_threads: PyTorch uses 8 threads, the
   physical cores of the 8-core, 16-thread CPU of benchmarks/2026-10-30/README.md:4). The NumPy trace uses one
   thread: NumPy ufuncs are single-threaded, and the numba kernels of Optiland's NumPy backend
   (optiland/backend/numpy_backend/conic.py:34, :72) are `@njit` without `parallel=True`. Thus the headline
   "7.3x (singlet) and 7.4x (4f) faster than NumPy" (README:91) is against ONE CPU thread. In the root README and
   in bands_gpu and thermal_gpu, "16 CPU threads" means the full CPU, so a reader reads this speed-up wrongly.
   Fix: write "against NumPy (one thread) and PyTorch (8 threads, torch.get_num_threads)". Optionally also give
   the GPU against the 8-thread PyTorch CPU trace at 1e7 rays (1.974/0.186 = 10.6x singlet, 1.426/0.138 = 10.3x 4f).
2. **minor** - optics_gpu/README.md:91-92. "with the copy to the host, 4.5x and 4.2x". From the JSON rows, 4f at
   1e7 rays: 1.0183 / (0.1381 + 0.1005) = 4.27, that is 4.3x (singlet 4.45 = 4.5x is correct). Fix: 4.3x.
3. **minor** - optics_gpu/README.md:92. "Below about 1e5 rays the GPU is slower". At 1e5 rays the GPU is not
   faster: singlet 0.0111 s against 0.0117 s (equal), 4f 0.0099 s against 0.0047 s (2.1x slower). The crossover is
   between 1e5 and 1e6 rays. Fix: "Up to about 1e5 rays the GPU is not faster (fixed cost per trace)".
4. **minor** - optics_gpu/src/optics_gpu/pop.py:199-201. A negative `ray_chunk` gives `range(0, n, -1)`, so the
   loop does not run and `propagate_through` returns an all-zero field with no error (reproduced: ray_chunk=-1 gives
   max|E| = 0.0; ray_chunk=0 falls back to the default). Fix: raise ValueError if ray_chunk is not None and
   ray_chunk < 1.
5. **minor** - optics_gpu/src/optics_gpu/pop.py:37 (and optics_gpu/README.md:49, pop.py:171 "so that large ray
   counts fit in memory"). The comment gives 512 MB for one chunk, which is only ex plus ey. The peak is about 2x:
   at the start of the next chunk the old ex and ey are still alive while the new complex product
   `1j*k*xi*Lo` and the new `exp` exist (old ex + old ey + 2 x new (Nx, chunk)), and `ex * ao` is one more
   (Nx, chunk) temporary. With Nx = Ny that is about 1 GiB of complex128. Fix: state the peak (about 2 x 512 MB),
   or `del ex, ey` at the end of each loop step and halve SUM_ELEMENTS if 512 MB is the target.
6. **minor** - optics_gpu/src/optics_gpu/pop.py:136-145. The reference trace of the 25 check rays runs on the
   caller's active backend. If a caller has set Optiland's PyTorch backend globally (its default float32), every
   `trace_rays(..., device="cpu" | "cuda")` stops with the RuntimeError "the optic does not survive Optic.to_dict /
   from_dict" (reproduced: largest difference 6.7e-8), which is a wrong diagnosis (the cause is float32 against
   float64). Fix: run the reference check under NumPy (or under the same float64 setting), or name the precision in
   the message, or document that the caller's backend must be NumPy.
7. **minor** - tools/env/optics_rocm.sh:12. `torch` is not pinned, but the rows and the README name
   2.14.1+rocm7.2. A later run of the script can install another version, so the bench rows cannot be reproduced
   with this script. tools/env/rocm_jax.sh pins its versions. Fix: `torch==2.14.1` (and optionally numpy/scipy at
   the versions of optics_gpu/uv.lock).
8. **minor** - .gitignore (tools/env/optics_rocm.sh:9). The script makes `.venv-optics` in the repository folder;
   `.gitignore` has `.venv/`, which does not match `.venv-optics` (the same is true of the existing `.venv-rocm`).
   If a clone on the GPU computer runs `git add -A`, a virtual environment goes into the public repository. Fix: add
   `.venv-*/` to `.gitignore`.
9. **minor** - optics_gpu/README.md:59 and :95-104. The check-table row says "difference 0, bit-identical" for the
   PyTorch CPU trace; that is true on the Mac only (the GPU-computer rows show 1e-14 mm and 7e-14 mm, as README:92
   says). The Mac timing table has no rows under benchmarks/ (no provenance). A re-run on this Mac (other sessions
   loaded it) gave NumPy 0.0016 / 0.0096 / 0.094 s and PyTorch 0.0047 / 0.0249 / 0.068 s at 1e4 / 1e5 / 1e6 rays,
   that is 1.5x to 3x slower than the table; the conclusion (PyTorch CPU slower below 1e6 rays, faster at 1e6;
   difference 0) is the same. Fix: add "(on the Mac)" to the row, and record the Mac rows in a JSONL file or mark
   the table as indicative.
