## Findings

1. **major**: tools/gpu_run.sh:13-14 and :38, addon_gpu/README.md:350-351. The SIGKILL does not reach the children
   of the command on the GPU computer. There, `timeout` is uutils coreutils 0.8.0 (`/usr/lib/cargo/bin/coreutils/timeout`).
   At the kill-after limit it sends SIGKILL only to the direct child, not to the process group. GNU timeout sends it
   to the process group. Evidence (all tests on the GPU computer, sleep only):
   - Test A, private lock: `flock -w 3 L timeout -k 2 2 bash -c "trap '' TERM; sleep 11.61 & sleep 11.62; wait"`
     gave rc 137 at 4 s. Both sleeps stayed alive, in the process group of `timeout`. The lock stayed HELD until
     they ended.
   - Test F, the real `tools/gpu_run.sh` with `GPU_RUN_TIMEOUT=2 GPU_RUN_KILL_AFTER=2` and the same command form:
     rc 137 at 4 s, then two survivor sleeps, each with an open fd on `.local/gpu.lock`.
   - The test of the author passes only because bash execs the last simple command of
     `bash -c 'trap "" TERM; sleep 20'`, so sleep is the direct child (test D: rc 137, sleep gone, lock free).
   - Test G: GNU timeout 9.7 is installed as `/usr/bin/gnutimeout`. Test A with `gnutimeout` gave rc 137, both
     sleeps gone, lock free at once.

   So the claim "a command that ignores SIGTERM cannot hold the GPU lock" is false for each command whose
   descendants ignore SIGTERM (a shell wrapper with `trap '' TERM`, a pytest worker that ignores TERM). Fix: use
   GNU timeout when it exists (for example `tmo=$(command -v gnutimeout || command -v timeout)`), and test with a
   command that has a TERM-ignoring child (the form of test A). If you keep the uutils `timeout`, change the comment
   and the README line to say that SIGKILL reaches only the direct child.

2. **minor**: tools/gpu_run.sh:13-14. Also with GNU timeout, two cases keep the lock after the limit. The comment
   does not state them.
   - Test B: the direct child dies on SIGTERM, but a descendant ignores SIGTERM. Then `timeout` returns 124 at
     once and never sends SIGKILL. Result: rc 124 at 2 s, grandchild alive, lock HELD until the grandchild ended.
   - Test E: a descendant in its own process group gets neither signal. Examples are a nested `timeout` (as
     `suite_runner.py --inner` makes for each module), `setsid` and `start_new_session=True`. Result: rc 124 at
     2 s, inner sleep alive, lock HELD for about 5 s more, until the inner limit.

   `flock` runs without `-o`, so these descendants keep the lock fd. This can be the wanted behavior, because the
   lock stays held while a GPU process runs. A process in uninterruptible sleep (a GPU driver hang) also ignores
   SIGKILL. For `suite_runner.py`, the outer `GPU_RUN_TIMEOUT` (chunk_seconds + timeout + 120,
   addon_gpu/suite_runner.py:414) is longer than the bound of each module (timeout + 30). Thus case E needs a
   hang of the inner runner itself. Fix: state the limit in the comment. Optional: after `timeout` returns, kill
   the rest of its process group (`kill -KILL -- -<pid of timeout>`).

## What the reviewer tried to break

- Process groups (the question of the lead): see findings 1 and 2. The uutils `timeout` 0.8.0 does `setpgid`
  (the survivors had the pgid of `timeout`) and sends SIGTERM to the group. It sends SIGKILL only to the direct
  child. GNU `timeout` 9.7 (`gnutimeout`) sends SIGKILL to the group. Neither sends a signal to a descendant in
  another process group.
- Lock release after SIGKILL: if no descendant survives, the lock is free at once (tests D and G, `flock -n`
  directly after the return). util-linux flock 2.41.3 forks; its child (`timeout`) inherits the lock fd, because
  `-o` is not used. The lock stays held while any survivor holds that fd (tests A, B, E, F).
- Exit codes: 124 (tests B and E), 137 (tests A, D, F and G) and 0 (`bash tools/gpu_run.sh meow_gpu true`)
  were reproduced. Callers: the only caller that sets `GPU_RUN_TIMEOUT` is addon_gpu/suite_runner.py:414. Its
  code at :427-431 stops on each non-zero exit other than 3 and 4, and does not compare 124 or 137.
  `TIMEOUT_EXITS = (124, 137)` (suite_runner.py:83) applies only to its own per-module `timeout`. A grep of
  tools/ and addon_gpu/ found no other use of 124, 137, `GPU_RUN_TIMEOUT` or `GPU_RUN_KILL_AFTER`.
- Shell quoting: the line continuation at tools/gpu_run.sh:37 has no trailing space. `"${GPU_RUN_KILL_AFTER:-30}"`
  is safe under `set -u`, and an empty value gives 30. `"$@"` keeps the arguments. `-k 0` (uutils) sends no
  SIGKILL: rc 124 after the command ended at 3 s, the same as GNU.
- README line 350: `suite_runner.py` uses `timeout -k 30` for each module (suite_runner.py:82 and :195), so the
  text "as `suite_runner.py` does" is correct. Finding 1 applies to that per-module call too.
- Hygiene: the diff holds no host name, IP address, private path or e-mail address.
- Scratch files on the GPU computer: empty lock files `/tmp/rv_c1663_lock`, `/tmp/rv_c1663_lockA`, `lockB`,

## Fixes by the author
1. (major, SIGKILL only to the direct child with the uutils timeout) Fixed: tools/gpu_run.sh:39-41 uses
   `tmo=$(command -v gnutimeout || command -v timeout)`, so the GPU computer runs GNU timeout 9.7
   (/usr/bin/gnutimeout), which sends both signals to the process group. The comment (tools/gpu_run.sh:12-18)
   says why. Test on the GPU computer (the lead, the reviewer's test F): `GPU_RUN_TIMEOUT=2 GPU_RUN_KILL_AFTER=2
   bash tools/gpu_run.sh meow_gpu bash -c "trap '' TERM; sleep 41 & sleep 42; wait"` gives exit 137 after 4.0 s,
   and no sleep is left (pgrep count 0), so the lock is free; `sleep 20` with GPU_RUN_TIMEOUT=2 gives 124, `true`
   gives 0. addon_gpu/README.md:350-352 says that gpu_run.sh uses GNU timeout and that suite_runner.py uses the
   timeout on the PATH (the uutils one on the GPU computer: SIGKILL only to the direct child); a change of
   suite_runner.py is a follow-up of the add-on package.
2. (minor, cases B and E) Fixed in text: tools/gpu_run.sh:16-18 states that a descendant keeps the lock (flock
   without -o) in its own process group (setsid, a nested timeout), when it ignores SIGTERM and the direct child
   ends at SIGTERM, or when it is stuck in the GPU driver. No kill of the group after timeout returns: the script
   ends with exec, and a wrapper shell would change the exit status path of every run; not needed for the callers
   of this repository (the reviewer: suite_runner's outer budget is longer than each module's limit).
