## Findings

No blocker and no major finding. The patches are correct on the installed CuPy 14.2.0, and every README number
that the reviewer checked agrees with the logged rows or the logs. Nine minor findings:

1. **minor** `addon_gpu/README.md:136`: wrong date of the crash. The README gives "2026-10-30, 16:49". The journal of
   the GPU computer shows that the boot before the crash ended on 2026-11-07 at 16:49:44 EST, and STATUS.md:22 also
   gives 2026-11-07. Fix: write "2026-11-07, 16:49".
2. **minor** `addon_gpu/README.md:136-137`: "about one minute after the start of a run of 6 test modules" does not
   agree with the file times. `.local/addon-runs/suite-subset-erised-fork.log` is empty, and the system made it at
   16:49:44.64. That is the same second as the last journal entry of that boot. The three Triton probe logs end at
   16:48:33, about 70 s before. Thus the crash came at the start of the module run, about 70 s after the Triton
   probes, which also agrees with "about 80 s after the GPU resumed". Fix: give these times, and do not name the
   module run as the probable trigger.
3. **minor** `addon_gpu/README.md:13, 119-131`: the end-to-end time is given for the 3-D case only. For the 2-D
   bench case, the logged rows give a whole run (setup and steps) of 22.0 s to 23.9 s on the GPU route against
   6.4 s on the CPU solver. Thus the GPU route is 3.4 to 3.7 times slower end to end, but the README does not say
   it. The table and the headline give only the step-loop speed-ups (5.0x to 28x). Fix: add a column "whole run" to
   the table. In the status paragraph, say that the 2-D bench case is slower end to end and the 3-D case is 1.1 to
   1.2 times faster.
4. **minor** `addon_gpu/README.md:116-122`: the precision is not given next to the speed-ups. The add-on steps in
   float32, and the CPU solver steps in float64. A step loop that is limited by memory bandwidth moves half the
   bytes in float32. Fix: write "float32 GPU against the float64 serial CPU solver" in the table header or in the
   line above the table. (The serial build is already stated at line 117 and in "Open items".) The whole-run figures
   also do not include the kernel compilation of a first run. With warm disk caches, the reviewer measured only
   0.4 s to 0.8 s more for a fresh process (small 3-D case), so this is a note only.
5. **minor** `addon_gpu/README.md:86`: "the 145 hand-written kernel modules" is wrong. In the pinned clone,
   `meep_gpu/cuda_kernels/` holds 145 `.py` files: 66 test modules, 1 `__init__.py` and 78 other modules. Of the
   non-test modules, 59 hold `__global__` kernel source. The claim "no warp intrinsic" is correct (no match in the
   whole folder, and no `__shared__` in a non-test module, so the kernels are elementwise). Fix: write "the 145
   Python files of `meep_gpu/cuda_kernels/` (59 non-test modules hold kernel source)".
6. **minor** `addon_gpu/subnormal_gate.py:7-10`: the statement "Under ``keep`` CuPy needs a kernel cache folder
   whose name carries ``ftz_stripped``" is not true for CuPy 14.2.0. CuPy 14 makes its disk cache back end
   (`_compiler_cache.DiskKernelCacheBackend`) once, when `cupy.cuda.compiler` is imported, and it reads
   `CUPY_CACHE_DIR` only then. The reviewer measured this: after `point_cupy_cache_at_keep_policy()`, the variable
   names `.local/cupy-cache-ftz_stripped`, but the back end still uses `.local/cupy-cache`.
   `.local/cupy-cache-ftz_stripped` has 0 files, and `.local/cupy-cache` has 341. Thus, on this CuPy, the move of
   the folder only satisfies the check of the add-on. The keep token that patch 0002 puts into the key is the only
   separation of keep binaries from flush binaries. The separation holds: 2 of 2 compiles after the keep install had
   the token in `key_src`, and 0 of 5 compiles before it had the token. Fix: correct the docstring. In
   `tools/env/addon_patches/README.md`, say that on CuPy 14 the token in the key is the only barrier against a stale
   flush binary.
7. **minor** `tools/env/addon_patches/0002-hip-keep-subnormals.patch:51`: `keyed(source, options, arch,
   extra_source=None, ...)` puts the token into the fourth positional argument. This is correct for CuPy 14.2.0
   (`_compile_with_cache_hip(source, options, arch, extra_source, backend=...)`, compiler.py:1003). CuPy 13 had
   `cache_dir` in that position. In CuPy 13, the token would become a cache folder that is relative to the current
   folder, and it would not go into the key. The failure would give no message. `tools/env/addon_gpu.sh:28` installs
   `cupy-rocm-7-0` with no version pin, and no test in `addon_gpu/tests/` makes sure that the token gets into the
   key. Fix: pin `cupy-rocm-7-0==14.2.0`, or find the position of `extra_source` with `inspect.signature`.
   Also add a test that spies on `compiler._hash_hexdigest` and asserts that the token is in the key of a keep
   compile (the probe of the reviewer does this in about 20 lines).
8. **minor** `addon_gpu/tests/test_patches.py:64-69`: the RawKernel test cannot see if `-ffp-contract=off` has an
   effect, because `0.5 * x + 1` is exact with and without FMA. The reviewer ran an operand pair that is sensitive
   to FMA (`a = b = 1 + 2^-12`, `c = -(1 + 2^-11)`; `a*b + c` is 2^-24 if fused and 0 if not fused). The results
   were: no option 5.96e-08 (fused, the default of hipRTC), `--fmad=false` 0.0, and `--fmad=true` 5.96e-08. Thus
   the translation has the correct meaning, and it is necessary. Fix: use these operands in the test, and assert
   0.0 for `--fmad=false`.
9. **minor** `addon_gpu/tests/test_parity.py:23, 90`: the resonance check became 100 times looser after a failure.
   `.local/addon-runs/addon-gpu-pytest-ring.log` (19:42) shows the first version: frequency to 1e-6 relative, which
   failed at 7.6e-6. The current version checks the complex frequency to 1e-4 of f, and the largest measured
   difference is 7.7e-6. The band is the band of the add-on, and the test comment states it, so the test is
   acceptable. But a tolerance of 2e-5 would keep a margin of 2.6 times and find 5 times smaller defects. Fix
   (optional): use 2e-5, or add a separate check of Q to 1 %.

## What the reviewer tried to break

- **Tests on the GPU computer.** The GPU computer answered (uptime 3:17, load 0.1, no other Python process) before
  each run. The Mac files and the GPU computer files have the same SHA-256, so no push was necessary. The work copy
  `.local/upstream/addon-work-3` equals the two patches exactly (`git diff` without the `index` lines has the same
  SHA-256 as each patch file). Command: `ADDON_GPU_CLONE=.../addon-work-3 bash tools/gpu_run.sh addon_gpu python -m
  pytest -q -rA`, with the export line and `CUPY_GPU_MEMORY_LIMIT`. Result: 19 passed in 71.75 s. The uptime
  continued, and the computer had no problem.
- **Patch 0001 (hipRTC options).** CuPy 14.2.0 appends `-fcuda-flush-denormals-to-zero` and the `-I` options in
  `_compile_with_cache_hip`, and it puts the options into the key `env` before the leaf compile. Thus the wrap at
  that entry point is necessary, and it is at the correct level. It runs only when `cupy.cuda.runtime.is_hip` is
  true, so NVIDIA and Apple do not change. The wrap and the keep keyer stack in both orders without a second layer,
  because `functools.wraps` copies `__dict__` (the reviewer saw both marks on the live entry point).
  `install_cupy_policy` calls the guard first, so a restore gives back the options wrapper. FMA semantics: see
  finding 8.
- **Patch 0002 (keep on ROCm).** The strip wraps `compile_using_nvrtc` (which also calls hipRTC) and
  `compile_using_hipcc`, so both HIP back ends are covered. On NVIDIA, `_cupy_is_hip` is false, the same entry
  point and wrapper are chosen, and the report text is the same; NVRTC options never hold the clang spellings.
  `install_cupy_policy` resolves `cupy` before the HIP test, so `_cupy_is_hip(None)` cannot occur. On ROCm 7,
  `_convert_to_hip_source` does not read `extra_source`, so the token changes the key and not the binary.
  **Stale cache:** a binary compiled before the patch has a key without the token, so a keep compile cannot read
  it. After the patch, only keep compiles (which strip the flag) write token keys. The add-on test
  `test_a_float32_ufunc_compiled_before_a_keep_install_keeps_subnormals_after_it[keep_directory]` fails on the
  pinned clone and passes with the patches (logs `mod-subnormal-pinned.log`, `mod-subnormal_policy-work3.log`).
  The probe of the reviewer under keep gave word 0x00004000 for 2^-70 * 2^-65 in a RawKernel, with and without
  `--fmad=false`. The cache-folder pointer has no effect on CuPy 14 (finding 6), and the signature risk is finding 7.

- **Fairness of the bench.** The case, the step count and the flux monitors are the same in all legs. The GPU loop
  time is honest: `FdtdDriver.run` calls `progress_cb` at the last step, and `run_case._progress` synchronizes the
  device there, so queued kernels are inside `loop_s`. `setup_s` on the GPU is `total_s - loop_s`, so it includes
  the init_sim of the solver inside the lift. A fresh process without a warm-up (small 3-D case, warm disk caches)
  added 0.26 s (hand-written) and 0.75 s (Triton) to the loop. The 3-D Triton loop holds about 1.4 s in its first
  100 steps that the steady rate does not show (cause not known). This makes the GPU look slower, not faster. For
  the open points about precision and the end-to-end time, see findings 3 and 4.
