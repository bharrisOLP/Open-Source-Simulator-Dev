## Findings
No blocker and no major finding. The code changes are correct (GMRES layout, thread for the post-processing,
OMP order), and every "after" number of the README matches the logged files. All findings are minor.

1. **minor: the OMP fix is not complete, but the README says that it is.** meow_gpu/README.md:208-209 says "The
   bench scripts now set it before the import of numpy". meow_gpu/bench/bench_eme_taper.py:21 still has
   `import numpy as np` at the top, and line 112 sets `OMP_NUM_THREADS` in `__main__`, after the import. This is
   the same bug, and the taper rows of the README come from this script. (bench_eme_batch.py and bench_refine.py
   import bench_eme_taper after they set the variable, so these two scripts are correct.) Fix: move the
   `setdefault` in bench_eme_taper.py above the numpy import, or name the three fixed scripts in the README.
2. **minor: "the pool is slower than one thread" is not a stable result.** meow_gpu/README.md:466 (and :207). The
   logged run gives a pool of 8 at 101.7 ms against 47.8 ms serial, but a pool of 4 at 50.0 ms (about equal). My
   run on the GPU computer with no variable gave serial 50.1 ms and a pool of 8 at 45.4 ms (a little faster). Fix:
   write "the pool gains nothing, and it was up to 2x slower than one thread in the logged run". The library has
   no control for this condition, and users of `compute_modes_gpu_batch` get no protection. Follow the
   "deterministic controls first" rule: limit the BLAS threads in `_host_map` (for example with `threadpoolctl`),
   or warn when OpenBLAS uses more than one thread. Also make a ticket for this control.
3. **minor: the post-processing futures are read only after all solves.**
   meow_gpu/src/meow_gpu/meow_backend.py:386-399.
   - If `post_process` raises, the error reaches the caller only after all GPU batches are done. Before this
     change, the error came at once.
   - The queue has no limit. If the post-processing is slower than the solves, the raw E/H arrays of all cells
     stay in memory with the Modes.

   The results are correct (see below). Fix: before you submit batch j, call `.result()` on the futures of batch
   j - 2 (or j - 1). This keeps the overlap, holds at most one batch in the queue, and raises an error early.
4. **minor: an unchanged sentence now contradicts the new profile.** meow_gpu/README.md:128 says "meow's
   post-processing, about 0.6 s on a CPU". The new profile gives 0.85 to 0.91 s (the "before" columns). The logged
   per-cell rows of meow-profile-batch.jsonl give `backend._modes` = 1.065 s (single) and 1.104 s (mixed) for the
   30 cells. Fix: change the sentence to "about 0.9 to 1.1 s".
5. **minor: the category rules of the profile table do not give the exact sums.** meow_gpu/README.md:173-178.
   - "copies (`put`)" is 6.3 % and 6.7 % only when `backend.put` (0.09 % and 0.13 %) is added. The text says that
     the rows that start with `backend.` are setup rows.
   - `_svqb_b` and `_svqb` are counted as device kernels. But profile_batch.py:85 lists them as host steps, and
     their exclusive time is Python and host code. Their device parts (`_gram_b`, `_combine_b`, `_gram`,
     `_combine`) have separate timers.

   The effect is 1.3 points or less. Fix: put `backend.put` under the copies, and move `_svqb`/`_svqb_b` to the
   host or Python row (or say where they go).
6. **minor: the "before" columns cannot be checked.** meow_gpu/README.md:169-171 and 180-195. These columns come
   from development runs that were not logged. The text says this, but the table header does not. Some statements
   use only these numbers: the 20.4 % host eigenproblems, the 48.2 % GMRES, and the 17.3 % / 7.1 %
   post-processing. Fix: log the b495484 runs in a "-before" jsonl, or mark the columns "not logged" in the header.
7. **minor: two statements go further than the evidence.**
   - meow_gpu/README.md:219 says "The device kernels are limited by their throughput, not by the fixed cost of a
     call". But the next bullet shows the Gram kernel at 75 to 84 GB/s (about 10 % of the card's bandwidth). With
     vmap, 8 members take 4.6 to 5.1x the time of one (a gain of 1.6 to 1.7x per member). Only the GMRES gains
     almost nothing (271 ms against 280 ms). Better: "the time grows almost in proportion to the work".
   - meow_gpu/README.md:200 and eigensolver.py:337-338 say that XLA transposed the basis with the old layout. The
     speed difference is measured, but no one looked at the HLO for the cause. Write it as the probable cause.

## What the reviewer tried to break
- **The tests.** I pushed the working tree. The remote copies of eigensolver.py, meow_backend.py, test_batch.py and
  kernel_reduce.py have the same md5 as the local copies. `bash tools/gpu_run.sh meow_gpu python -m pytest -q`:
  **93 passed** in 157 s.
- **The numerics of the GMRES layout change.** I compared `kernel_reduce.krylov_before()` with the old code of
  the patch line by line, and they are the same kernel. I then ran the old layout, the new layout and a
  complex128 reference of the same algorithm (the same M values, `PC_DTYPE` = complex128). The inputs were the
  taper cell (36k unknowns), b = 18, a zero rhs row (an inactive pair), and different theta values. Results:
  - H, relative to max |H|, between the two layouts: 0, 7e-8, 3e-7 and 8e-5 at 1, 2, 5 and 20 steps. Against
    the complex128 reference, both layouts have the same error (2.1e-4 at 20 steps; small H entries).
  - The GMRES solution t: old against new 5e-7 relative. Old against the reference 6.6e-7, and new against the
    reference 6.7e-7.
  - The zero row stays zero in V and in t. Max |V^H V - I| = 1.9e-7.

  Conclusion: the orthogonalization order and the least-squares step are unchanged. The differences are complex64
  rounding only.
- **The GMRES timing.** I measured it again on the GPU computer: old layout 78.0 and 78.2 ms, new layout 35.3 and
  35.6 ms. This agrees with the logged 77.9 and 35.0 ms. The vmap numbers (271 ms against 8 x 35.0 ms) agree
  with the log.
- **The OMP claim.** I read the HEAD versions of bench_eme_batch.py and bench_refine.py. In both, numpy was
  imported at the top and the variable was set in `__main__`, so the claim is true. On the GPU computer, the
  OpenBLAS variables were unset and I timed eig on 8 matrices of 72 x 72:
  - no variable: serial 50.1 ms, pool 45.4 ms.
  - variable set after `import numpy`: serial 48.1 ms, pool 60.8 ms (no effect).
  - variable set before `import numpy`: serial 31.6 ms, pool 5.2 ms.

  So the variable must be set before numpy loads, as the patch does. bench_eme_taper.py is still wrong
  (finding 1).
- **Thread safety of the post-processing thread (code reading).**
  - `solve_batch` returns new host arrays. `np.array` makes a copy, and the fancy index in `_orient` makes
    another.
  - The solver memory holds only device vectors. Nothing in the GPU solve path writes to the arrays that the
    thread reads.
  - meow's `Mode`, `post_process` and `inner_product` use numpy only (no JAX). meow's `cached_property` is a dict
    for each instance; at the same time, it can only compute the same value twice.
  - The `_host_map` pool and the post thread share no state.
- **Thread safety (run on the GPU).** I used a 7-cell taper with batch 3. The last run is short, so cell 6 is
  solved again while its post-processing can still run. A `_modes` wrapper slept 0.2 s, so that the solves and
  the post-processing ran at the same time. Results:
  - All post-processing ran in the thread `meow-gpu-post_0`.
  - 0 inputs changed between the return of `solve_batch` and the post-processing.
  - All fields, neff and cs were bitwise equal to a post-processing in the main thread from the same inputs.
- **Exceptions and order.**
  - Fallback cells use tidy3d in the main thread, before the batches (unchanged).
  - `out[c]` is set by the cell index, so the order of the input stays.
  - A post-processing error raises at `done.result()` (the new test covers this).
  - If a solve raises, the `with` block waits for the queued post-processing, and then the solve error goes to
    the caller.
  - Errors come late (finding 3).
- **The new test.** It checks 3 post-processing calls (the duplicate cell is not post-processed), none of them in
  the main thread, and that an error reaches the caller. It does not check the overlap itself; the bench numbers
  show the overlap.
- **The README numbers against the logged files.**
  - Batch table (eme-batch-profiled.jsonl): all times, speedups (1.86 / 1.67 / 1.31 and 1.20 / 1.15 / 1.08),
    dneff, iterations (474/480, 164/165, 105/101, 72/68), the S21 ranges, the cold batches (52/49) and the mode

  - Comparisons with earlier rows: 5.53 s (eme-batch.jsonl) and 11.72 s (meow-refine.jsonl) are correct.
  - Refinement table (meow-refine-profiled.jsonl): 23.01 / 7.91 / 4.37 s, 21166 / 1722 / 0 applies,
    1081 / 480 / 474 iterations, the S21 values, 2.7e-12 and 5.1e-6, 1.8x (2.1x before = 11.72 / 5.51), 2.9x,
    and the residuals 9.3e-11 / 9.96e-11 are correct.
  - Profile "after" columns: I added the shares of the JSON parts with the stated mapping. Every row is correct
    (53.5, 7.7, 2.9, 6.3, 15.7, 5.4, 8.5 for single; 17.3, 36.7, 15.3, 3.1, 2.4, 6.7, 13.1, 2.2, 3.2 for mixed),
    with the small differences in the mapping of finding 5. Run 3 / run 2 / per-cell times and "1.9 to 3.4 s"

  - kernel_reduce numbers (35.0 / 77.9, 271, 5.4 / 31 / 102 / 48 ms, Gram 0.31 to 0.35 and 1.59 to 1.60 ms,
