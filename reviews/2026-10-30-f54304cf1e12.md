## Findings

No blocker. One major finding. Seven minor findings. The bend operator, the PML speeds with mu, the field
back-transform and the direction rule are correct (checks below). The major finding is in the warm start of the
batched solve.

1. **major** - `meow_gpu/src/meow_gpu/meow_backend.py:168-174, 186-187, 252-259`. The batched solve gives a member
   the warm start of a cross-section of a different kind. The module docstring and `_memory_key` say that a
   cross-section starts only from the modes of the same kind, but `solve_batch` breaks this rule in two ways:
   - `batch_key` keeps only the bend keys, without the member positions. So `[bend 5 um, straight]` and
     `[straight, bend 5 um]` have the same key, and member i starts from member i of the other batch.
   - When `batch_key` is not in the memory, `key = _memory_key(problems[0], b)` gives the vectors of the kind of
     member 0 to ALL members (`jnp.broadcast_to`).

   Evidence (GPU computer, the strip of `tests/test_bend.py`, 4 modes, `extra=4`):
   - Through the public API: `compute_modes_gpu_batch([bend5, straight, straight, bend5], num_modes=4, batch=2)`,
     mixed precision. The function warns "did not converge for 1 of 2 problems of the batch (largest residual
     3.5e-01)". Cell 1 (straight) gives neff 2.451838, 1.787314, 1.506118, 1.436607; the per-cell solve gives
     2.451829, 1.787313, 1.506117, 1.343646. Cell 3 (bend) converges with NO warning, but to another mode set
     (1.581894, 1.474774 instead of 1.65788, 1.581894). The docstring says that the results are those of
     `compute_modes_gpu`.
   - `solve_batch([b5, s])`, then `solve_batch([s, b5])`: the straight member stops at 500 iterations, residual
     0.32 (double) / 0.35 (mixed), neff off by 0.09.
   - `solve(b5)`, then `solve_batch([b5, s, b10, b50])`: the straight member stops at 500 iterations (residual
     0.28 / 0.37, neff off by 0.09). In mixed precision the 50 um member converges to another 4th mode (off by 0.11).
   - The new test `test_batch_with_bends_and_straight_cells` solves one batch from a cold start, so it does not
     find this.

   The memory key also ignores `plane_center`. A different plane centre changes the problem as much as a
   different radius does.

   Fix: make the batch key the ordered tuple of the member keys (`(nbat,) + tuple(_memory_key(p, b) for p in
   problems)`). For the fallback to the per-cell memory, give each member the vectors of its own key, and give a
   random preconditioned block to members without one, or warm-start only when all members have the same key. Put
   `plane_center[norm_axis]` (or the shifted coordinate) into the bend key. Add a test: the list `[bend5, straight,
   straight, bend5]` with `batch=2` gives the per-cell results, and `solve(b5)` followed by `solve_batch([b5, s])`
   gives them too.

2. **minor** - `meow_gpu/tests/test_bend.py:65-69, 105-108`. No test checks Ez or Hz of a bend, but these are the
   only components that the back-transform changes (`operator.py` `fields`: Ez = a_e Ez', Hz = a_h Hz').
   `meow.inner_product` uses only Ex, Ey, Hx and Hy, and the 4-mode test uses only Ex and Ey. The reviewer compared
   all six components with `compute_modes_tidy3d` (double, 2 modes; R = 5 um on both axes, R = -5, 2 and 10 um).
   Each component agrees to 3.4e-10 to 2.6e-8 relative. The exception is the second mode at R = 2 um: there the two
   solvers give different modes (GPU 2.2575, a box mode that tidy3d misses; tidy3d 2.1493). Without the Jacobian,
   Ez and Hz differ by 1.4e-2 to 1.1e-1. So
   the code is correct, but a regression in the back-transform would pass the tests. Fix: in
   `test_bend_modes_match_tidy3d`, compare Ez and Hz (after phase alignment) with the tidy3d modes.

3. **minor** - `meow_gpu/README.md:269-270` against `meow_gpu/bench/bench_bend.py:11, 90`. The README says "the best

## What the reviewer tried to break

- **Patch against the working tree.** The git blob hashes of all 11 files in the working tree are the same as the
  `index` lines of the patch. The SHA-1 of `operator.py`, `meow_backend.py` and `test_bend.py` on the GPU computer
  after `remote.sh push` is the same as on the Mac.
- **Test suite on the GPU computer** (`bash tools/gpu_run.sh meow_gpu python -m pytest -q`): 82 passed in 89.8 s.
  The reviewer counted 34 new tests (24 in test_bend.py, 9 in test_operator.py, 1 in test_meow_backend.py).
- **Transform against tidy3d 2.12.2 source** (`tidy3d/components/mode/transforms.py`, `solver.py`,
  `derivatives.py`). The patch has the same norm axis, the same shift u = coord + R - plane_center, a_e = R/u[:-1]
  and a_h = 2R/(u[:-1]+u[1:]), and the same `expand_dims` axis. eps' = J eps J^T / det J gives eps_xx/a, eps_yy/a,
  eps_zz a. mu' gives 1/a_h, 1/a_h, a_h. `p_mu` = [[0, mu_yy], [-mu_xx, 0]], and `q_partial` has inv_mu_zz. These are
  the same as in `solver_diagonal`. `apply` and `fields` (Hx, Hy from q u / (i neff - keff), Hz = inv_mu_zz curl, Ez
  from q_ep u) are the same as in tidy3d. `average_relative_speed` is 1/sqrt(mean eps * mean mu) on the transformed
  tensors, as in `pml_speeds`. The target comes from the physical eps, as in tidy3d (`eps_physical`). The
  test `test_bend_operator_equals_tidy3d` captures the matrix of tidy3d's own `compute_modes`, so it covers the
  transform, the PML and the media together.
- **Field back-transform** (E = J^T E', H = J^T H'): it is the same as tidy3d `np.sum(jac_e[..., None] * E[:, None,
  ...], axis=0)`. All six components agree with tidy3d (finding 2). The direction rule: tidy3d flips E'z, H'x and
  H'y before J^T. The patch flips after J^T. These commute, and Pz uses only the transverse fields, which J does not
  change.
- **Straight results unchanged.** For a straight problem: `mu`, `jac` are None, `apply`/`fields` take the old
  branch, `pml_speeds(..., None)` gives the old value, `eps_max` is the old max |eps|, the memory key is
  `(shape, b)`, and a batch without bends gets no bend arrays. The 48 old tests pass at their old tolerances.
- **Warm start.** Per-cell `solve` is correct (one key per kind, the new test). The batched path is not
  (finding 1). A script on the GPU computer showed this, and the reviewer then reproduced it through
  `compute_modes_gpu_batch`.
- **README numbers against the JSON rows** (20 nm, 18 rows + 3 PML rows). Mixed 0.215-0.298 s, single
  0.168-0.250 s, double 0.472-1.036 s, tidy3d 0.296-0.428 s, PML 1.411 / 0.519 / 0.288 s with 271 / 90 / 48
  iterations, and tidy3d 0.393-0.416 s. All agree with the README. The exceptions are findings 3 and 4.
- **Re-run of the README bench commands** (40 nm and 20 nm, double, and the 4-mode mixed row) on the GPU computer.
  max |dneff| 3.3e-12 / 2.0e-12 / 3.5e-12 / 2.0e-12 / 2.0e-12 / 3.8e-12. Against the straight modes: 4.99e-3 /
  7.92e-3 / 6.31e-4 / 3.22e-5 / 3.23e-6 / 3.23e-7. With PML: 8.6e-13, 2.7e-13, 7.6e-13; Im 3.9648434595e-5 /
  3.9648434782e-5, 9.8201448e-7 / 9.8201469e-7, 2.4136e-9 / 2.4130e-9. R = 1.5 um: 500 iterations, not converged,
  residual 1.02e-10. R = 2 um: 199 iterations. Mirror bends: 2.459752 - 2.446844 = 1.29e-2 (40 nm), 2.448070 -
  2.441941 = 6.1e-3 (20 nm). 4-mode row: tidy3d 2.4468, 1.8002, 1.5969, 1.4822 and the GPU 2.4468, 1.8002, 1.6579,
  1.5969 (common modes 2.2e-14). R = 50 um: all 4 agree (5.0e-11). All agree with the README (finding 6: only
  the record is missing).
- **The first-order discretization error.** The reviewer checked it with the tidy3d source: `dwdz_e` uses
  `coords[:-1]` for all E components, so Ex (at the cell centre in x) is half a cell off. An estimate of
  dx/(2R) * neff gives about 5e-3 per bend at 40 nm and R = 5 um. That agrees with the 1.29e-2 mirror difference.
  For a symmetric guide, the physical change from straight is of order 1/R^2, so the 1/R part comes from the
  discretization, as the README says.
- **Box modes that tidy3d misses.** tidy3d calls `eigs(k=num_modes, sigma, v0=random)`. The test with k = 8 and
  tol 1e-13 on the captured matrix confirms the GPU set in double. In mixed precision, the GPU solver also misses
  such modes (finding 5).
- **Fallback tests.** The two changed tests patch the module-level `_supported`, which `compute_modes_gpu` and
  `compute_modes_gpu_batch` use. The tidy3d path still runs for a bend. The patch does not weaken any assertion.
- **Other packages.** No code outside `meow_gpu` uses a bend radius with meow_gpu (grep).
- **Hygiene.** The patch has no host names, IP addresses, private paths, e-mail addresses, client or PDK data. The
  device string is `rocm:0`. The structure uses textbook indices. License: `radial_transform` is a re-implementation
  of about 10 lines of the tidy3d mode solver (MIT, Flexcompute / ceviche), and its docstring names the source. It
  is not a finding of this change, but a NOTICE for the tidy3d-derived code of `meow_gpu/fde` would be good.
