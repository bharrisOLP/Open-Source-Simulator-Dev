## Findings

No blocker. Two major findings (one documentation claim with no evidence, one silent-result path in the new
suite). The multigrid itself is correct: the Galerkin coarsening is exact, and the V-cycle is symmetric positive
definite for every grid that I tried (proof and experiments in the next section).

### Major

M1. **README.md:10, STATUS.md:70-71 against thermal_gpu/README.md:48 (major, unsupported timing claim).** The top
README ("2.9 million cells in 0.21 s") and STATUS ("Heater stack at 5 nm (2.9 million cells): 0.21 s on the GPU")
give a GPU multigrid time. The thermal README of the same commit says "GPU timings with multigrid: next run". The
commit holds no log, bench row or record of a GPU multigrid run, so one of the two statements is wrong, and the
headline number of the public README has no evidence. (Plausibility only: on the Mac CPU the same 5 nm solve took
0.74 s with 27 iterations; the reviewer did not use the GPU computer.) Fix: put the GPU run (command, log or JSON
row) into the commit and make the three files agree, or remove the number until the run is done.

M2. **suite/src/photonsuite/physics.py:83-85, :116, :123-128 and suite/README.md:8-19 (major, silent
non-convergence).** The suite drops every convergence flag: `temperature()` does not return or check
`SteadyResult.converged`, and `carriers()` / `modulator_vpil()` do not check `Solution.converged`. The README
snippet does not enable `jax_enable_x64`, so all solves run in float32 (dtype=jnp.float64 silently becomes
float32). Repro (the README structures, no x64):
- charge at 2 V: `converged False`, 200 Newton steps (max_newton), and `modulator_vpil` still returns V_pi L
  (1.6007 against 1.5996 V cm with x64) with no warning;
- thermal: `solve_steady` reports `converged True`, residual 7.8e-13, but the true residual of A T = b is 1.5e-6
  (MG) and 1.2e-5 (Jacobi): `converged` uses the recursive CG residual (solver.py:161, :80), which float32 can
  drive below 1e-12 while the true residual cannot go there. P_pi 19.047 mW against 18.997 mW with x64.
The numbers are close in these two cases, but the API gives no way to see a failed solve, and a hard case
(anisotropic cells, see m1) has no limit on the error. Fix: raise or warn in the suite when a solve is not
converged (and pass the flag out in `Temperature`); enable x64 in the README snippet (or in `photonsuite`
import, or refuse float32); optionally compute the true residual once after the CG loop in `pcg_mg` / `pcg`.

### Minor

m1. **STATUS.md:70, solver.py:71 ("about 20 iterations at any grid size"), STATUS "(Jacobi: 800 to 36000)".**
The 17-27 range holds for the heater stack with square cells (measured 17 / 21 / 24 / 27 at 50 / 20 / 10 / 5 nm:
it grows by about 3 per halving). Other cases: random 30/70 mix of 148 and 1.4 W/m/K, square cells: 54; cells
with aspect 1:5: 143; aspect 1:25: 624 (cap is 2000). Also, "Jacobi: 800 to 36000" compares thermal per-solve
counts with charge per-bias-point counts (charge MG per bias point is 226 to 560). Say "on the heater stack".

m2. **thermal_gpu/src/thermal_gpu/multigrid.py:88 (`np.linalg.pinv` with the default cutoff).** For a nearly
singular operator (pure Neumann plus a tiny Robin or extra term, about 1e-12 of the face conductances) pinv drops
the near-null mode (32 x 32 test: max eigenvalue of the coarse inverse 124 instead of about 1e15). On a grid of
1024 cells or fewer the preconditioner is this pinv alone, so M^-1 is singular there and CG cannot reduce that
mode. Realistic heater cases (h = 0.01 to 10 W/m^2/K, pure Neumann with a consistent right-hand side) converged
correctly. Consider `np.linalg.inv` for a nonsingular coarsest matrix, or a cutoff relative to the diagonal.

m3. **thermal_gpu/src/thermal_gpu/solver.py:113-117 (transient).** `pcg_mg` is capped at 2000 iterations per
step and the result is not checked or reported (`TransientResult` has no flag). It was silent before too (cap
200000); MG with C/dt converges fast, but say so or add a flag.

m4. **suite/src/photonsuite/geometry.py:41 with physics.py:46 (Yee samples on shape edges).** `Rect.contains`
is strict, and the Ex / Ez samples sit on the grid edges, which often coincide with shape edges. Inside or
outside then depends on the rounding of `np.arange`: with Window(..., -0.9, 1.1, 0.02) the edge "0" is
+7.8e-16 (inside Si) and "0.22" is 0.22 + 9.7e-16 (outside), so Ex / Ez see the core half a cell lower. All
window origins that I tried round the same way (neff equal to 1e-6), and the example uses the same rule, so the
test cannot see it. Consider a small tolerance or sub-pixel averaging.

m5. **suite/README.md:34, STATUS.md:75 ("within 1e-3") against suite/tests/test_workflows.py:22.** The P_pi check
is abs 0.05 mW around a rounded 19.0 (2.6e-3). The actual suite value is 18.997 mW (x64), so the claim is
probably true, but the test does not check it.

m6. **suite/src/photonsuite/physics.py:103-116 (`carriers`).** The docstring says left = p and right = n, but
`charge_gpu.solve` sets each contact voltage from the mean doping under it, so the v_p / v_n given to `Contact`
are ignored; any semiconductor that touches a window side (for example a Si substrate) becomes a contact, and a
side with mixed doping gets one voltage. Document this.

m7. **thermal_gpu/README.md:46-47.** The Jacobi GPU timings cite `bench/bench_steady.py`, but that script now
runs the MG default (no `--precond` option), so it can no longer reproduce the cited numbers.

m8. **thermal_gpu/src/thermal_gpu/solver.py:72, charge_gpu/src/charge_gpu/poisson.py:239.** An unknown `precond`
string silently selects Jacobi. Raise a ValueError.

m9. **charge_gpu/src/charge_gpu/poisson.py:242.** `extra0 = diag - face_sum` is exact in float64 (checked: 18
nonzero cells, the 18 contact cells, min 0.0). With `dtype=jnp.float32` the stored diag and gx are rounded and
the difference leaves noise of about 1e-7 of the diagonal, possibly negative, in every cell. Build the contact
conductances directly in `_operators` instead.

m10. **STATUS.md:67 and :47.** "Next: multigrid preconditioner" lines are now stale. bands_gpu/README.md:47-49 and
README.md:9 give new GPU timings (5.2 s / 60.3 s, 17.6 s, 11.7x to 15.6x) with no log in this commit; the
reviewer could not check them.

- SPD of the V-cycle (theory): with S = (I - w D^-1 A)^2 and the same smoother before and after, the operator is
  M^-1 = (I - S^2) A^-1 + a S P B_c P^T S^T. The first term is w g(w D^-1 A) D^-1 with g(t) = (1 - (1 - t)^4) / t,
  which is positive for t in (0, 2); here t <= 0.8 * 2 = 1.6 because each level (also the Galerkin coarse levels)
  is a weakly diagonally dominant 5-point M-matrix. The second term is positive semidefinite for any a > 0 when
  B_c is (induction; pinv of an SPD matrix). So OVERCORRECT = 1.6 cannot break definiteness; it only widens the
  spectrum of M^-1 A (seen up to 6.5).
- SPD of the V-cycle (numbers): formed the dense M^-1 with COARSEST = 4 (4 to 6 levels) for 23x19, 1x101, 101x1,
  17x2 and 21x15 grids with log-uniform kappa from 0.026 to 148: asymmetry <= 1.6e-15, min eigenvalue of M^-1 > 0,
  eig(M^-1 A) in [0.03, 6.6]. A nearly pure Neumann 15x15 case gave a min eigenvalue -0.09 against a max near 1e12:
  rounding of the kept near-null mode, not indefiniteness.
- Galerkin coarsening: compared `_coarsen` with an explicit sparse P^T A P for 7x5, 8x9, 1x9, 9x1, 2x7, 3x3, 2x2,
