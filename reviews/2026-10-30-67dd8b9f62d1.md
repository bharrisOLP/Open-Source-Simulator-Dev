## Findings

The main claim (meow 0.15 averages neff in Gram-Schmidt, and the new post-processing keeps it) is correct and well
supported. Two majors are silent wrong-physics paths in the new code. Each has a one-line fix.

1. **major**: `meow_gpu/src/meow_gpu/meow_backend.py:172`. The fallback path of `compute_modes_gpu` (bend radius,
   angled propagation) calls `mw.compute_modes_tidy3d(cs, num_modes=num_modes, target_neff=target_neff)` without
   `post_process`. So it uses meow's default `post_process_modes` and returns the averaged neff again, also when the
   caller passes its own `post_process`. Evidence: `meow.compute_modes_tidy3d` signature has
   `post_process: Callable = post_process_modes` (meow's version); line 168 sets `post_process`, but line 172 does
   not use it. The docstring (lines 3-13) and `meow_gpu/README.md` ("compute_modes_gpu therefore uses
   meow_gpu.meow_backend.post_process_modes") say that it always keeps the neff. Bends are the case where the higher
   modes matter most. Fix: pass `post_process=post_process` at line 172. Add a test: a cross-section with a finite
   `bend_radius` (or a monkeypatched `_supported`) gives the raw neff for each mode.

2. **major**: `suite/src/photonsuite/eme.py:61` (and `:51`). Each shape gets `mesh_order=1`. meow groups the
   structures of one `mesh_order` by material (`meow.cell._classify_structures_by_mesh_order_and_material`) and draws
   each material group at the position of its first structure. So the documented fill order of the suite
   (`suite/src/photonsuite/geometry.py:3`: "a later shape replaces an earlier one where they overlap") is lost when
   one material occurs before and after another material in overlapping shapes. Evidence (scratch run): shapes
   (SiN slab, SiO2 trench, SiN core inside the trench). `CrossSection.sample` gives the SiN core at (0, 0.1); the
   meow cell that the adapter builds gives n = 1.444 there, so the core is missing. The result is wrong and has no
   warning. The FDTD adapter is not affected (fdtdx sorts by `placement_order`, stable, and later objects
   overwrite). Fix: give each shape a distinct `mesh_order` that decreases with the fill order (for example
   `len(seg.xs.shapes) - j`), with the background above all of them. Add a test with overlapping mixed-material
   shapes that compares the meow cell index with `CrossSection.sample`.

3. **minor**: `meow_gpu/src/meow_gpu/meow_backend.py:12`. "|S21|^2 0.955 instead of 0.997" gives the 25 nm FDTD
   value (0.997) as the correct one. The documents of this change say that this value has an error of about 0.3 %,
   and that the corrected EME gives 0.991. Fix: "0.955 instead of 0.991 (3-D FDTD: 0.9945)".

## What the reviewer tried to break

- **Claim 1 (neff averaging in meow 0.15)**: I read the installed meow 0.15.0 source. `Mode.__add__` returns
  `neff=0.5*(self.neff+other.neff)`. `__sub__` is `self + other*(-1.0)`, and `__mul__` keeps the neff. So each
  Gram-Schmidt subtraction averages the neff, for all projection coefficients, also for 0. `orthonormalize_modes`
  calls `normalize_modes` and then Gram-Schmidt. `post_process_modes` calls `filter_modes` (PML, lossy) and then
  `orthonormalize_modes`. The new `meow_gpu.meow_backend.post_process_modes` does the same steps with the same
  default inner product and `gm_tolerance`. CONFIRMED.
- **Same as meow except the neff**: a scratch script applied both post-processings to tidy3d raw modes of a
  0.5 x 0.22 um strip (6 modes, dx = 40 nm and 20 nm). The six field components of all kept modes were
  bit-identical (max difference 0). The neff of meow_gpu is equal to the raw neff. meow gives 2.120 / 2.049 / 2.029
  for modes 2 to 4. The `interpolation` field is dropped on both sides (meow's `__mul__` also drops it), so that
  is not a new difference.
- **Is it correct to keep the neff of the leading mode when Gram-Schmidt mixes modes?** The default inner product
  is unconjugated, and distinct eigenmodes of a reciprocal guide are orthogonal under it. The measured projection
  coefficients after normalization are at most 6e-3 (40 nm) and 3e-3 (20 nm), mostly between modes near cutoff.
  The Gram matrix of the result has off-diagonal values of about 1e-4. For degenerate modes, a mix has the same
  neff, so the result is exact. For non-orthogonal modes with different neff, the mix is not an eigenmode. Keeping
  the neff of the main part has an error of order |c|, but the averaging has an error of order delta-neff for all
  c. PML and lossy modes are removed before Gram-Schmidt. The correction is sound. A possible improvement: warn when
  |c| is large, for example more than 0.1.
- **Claim 2 (Prism along z)**: the source is `if z < self.h_min or z < self.h_max: return []`. CONFIRMED. I swapped
  `photonsuite.eme._z_prism` for the upstream `mw.Prism`: T = 2.70e-29 (the documented value). With the fix, T =
  0.999999. I checked that the straight-guide test can fail: with no core, T = 0.032. So the EME tests can find
  these errors.
- **Claim 3 (x64 context)**: `jax.enable_x64` is a thread-local config `State` (Mac suite environment: JAX
  0.12.0.1; the GPU environment uses 0.11.1). Inside the context, the config value is False and the default dtype
  is float32. After the context, the value is True again. After an exception in the context, it is also True
  again. Another thread sees True during the context (fdtdx runs in the calling thread, so this is not a problem).
- **Claim 4 (Polygon edge rule)**: 300 random grids (steps 10 to 100 nm, also 1/30 um) x 2 vertex orientations. An
  axis-aligned Polygon and the Rect with the same corners gave the same samples in every case. The only difference
  is a sample exactly at x0 - EDGE_TOL (Rect includes it; Polygon excludes it), which does not matter. Problems
  with list vertices and invalid polygons: finding 11.
- **Calibrated FDTD measure**: I read the fdtdx 0.6.3 source (uv cache). `compute_overlap` is
  (1/4) integral of (E_m x H* + E* x H_m); for lossless guides, the conjugate power orthogonality removes the
  cross terms, so |a_out|^2 = eta * P_fund. The phasor flux is 1/2 Re(E x H*) through the plane. Then
  T00 = (P_out/P_in) * (eta P_fund/P_out) / (eta P_cal/P_cal) = P_fund/P_in. The bias eta cancels because the
  output detector, the window and the mode are the same in the calibration run. The formula is correct. `filter_pol="te"`
  selects E along fdtdx axis 1 = the suite x axis (horizontal), so it is the TE-like mode, as in the EME. The
  input flux plane is at z = 1.0 (the start of the taper). Reflection is about 4e-6 in power, so it does not
  matter.
- **Numbers in the documents against the JSON rows**: every number agrees with a row (|S21|^2 = S21_00^2).
  0.9867 / 0.9900 / 0.9912 / 0.9899 (20 modes); old 0.9546 / 0.9552 / 0.9471; 0.952 = 0.97570552^2 (30 cells,
  meow_gpu README table and `T_eme`); P_right + P_left = 0.99397 (corrected) and 0.99416 (meow), so 3.96 % into the
  higher modes; T00 0.99692 / 0.99780 / 0.99452; T_flux 1.00139 / 1.00147 / 0.99968; T_overlap 1.00406 (20 nm);
  straight T = 0.99999947, 10.73 s, 3 326 400 cells (220 x 140 x 108, recomputed); 8.37 M and 15.14 M cells
  recomputed from the windows; 212.9 s. "Agree within about 0.4 %": 0.9912 against 0.9945 is 0.33 %, and the FDTD
  changes by 0.25 % from 25 nm to 20 nm, so this is fair. Exceptions: findings 4, 5 and 7. The two calibrated 25 nm
  rows both have `seconds: 99.3` and the same `f_cal`. For a deterministic calibration run with the same step
  count, this is plausible.
- **Tests**: `meow_gpu`: 14 passed. `suite`: 9 passed, 1 skipped (`test_fdtd.py`, no fdtdx on the Mac; the GPU
  result cannot be checked here). `uv lock --check` in `suite/`: the lock file is current (shapely was already
  locked through meow). The working tree did not change.
- **Untested paths**: the fallback of `compute_modes_gpu` (finding 1); overlapping shapes in the EME adapter
  (finding 2); `interface_kwargs`; segment-length limits and backgrounds per segment (finding 8); the Gram-Schmidt
  drop branch (finding 10).
- **Public-data hygiene**: I searched the staged diff for home paths, user names, e-mail addresses, IP addresses,
  host names, PDK, client and process names. I found none. All materials are textbook indices (Si 3.476,
  SiO2 1.444), and all structures are synthetic. `tools/env/rocm_jax.sh` adds only public package pins.
