## Findings

1. **major** - bands_gpu/README.md (the paragraph after the slab table: "The error falls irregularly ... the
   averaging of eps does not give a clean second order there ... At 1025 points, `--sub 8` gives the same errors
   as `--sub 256` to 3 digits"; and the row "`--case slab --n 4097`, double precision | 4.05 s | not run | the 4 slab
   modes") and benchmarks/2026-10-30/bands-findk.jsonl:5. The cause that the README gives is not supported, and the
   committed row contradicts the convergence text without a word in the README.
   - Evidence (reviewer runs of `bench/bench_find_k.py --case slab` on the GPU computer, relative kmag error against
     the exact supercell, TE0 / TE1 / TM0 / TM1):
     - n 4097, sub 8 (the committed row): +1.63e-5, +1.03e-4, +4.13e-5, +8.02e-5. These errors are larger than
       at n 1025 and have the opposite sign.
     - n 4097, sub 256: +7.2e-7, +5.3e-6, +1.9e-6, +4.7e-6 (14x to 23x smaller; only `sub` changed).
     - n 2049, sub 256 (the README row): -5.74e-6, -2.38e-5, -1.36e-5, -1.02e-5; n 2049, sub 2048: -4.45e-6,
       -1.58e-5, -1.03e-5, -3.97e-6 (a change of 1.3x to 2.6x from `sub` only).
     - n 1025, sub 8 and sub 256: the same to 10 digits. The cause: at n 1025 the slab face (y = 0.25) is at exactly
       1/4 of a voxel, so 8 samples resolve the fill fraction exactly. At n 4097 the face is at 0.85 of a voxel, sub 8
       gives 7/8, and the slab is 6e-5 a too thick (relative 1.2e-4), which is the size and the sign of the error.
   - So the irregular convergence (and the 4097 row) comes mainly from the quantized fill fraction of the subpixel
     samples (a face position error up to dx / (2 sub), first order in dx), not from the averaging formula. The
     sentence on sub 8 is true only for n 1025 and suggests that the default `sub = 8` is sufficient, which it is
     not for a flat face at a general position.
   - Fix: give the sub dependence and the errors of the 4097 row in the README (or run it again with `--sub 256`
     and keep both rows); replace the explanation with the measured sub dependence; say that the 1025 agreement is
     a property of that grid; say that the default sub 8 limits the position of a flat face to 1/16 of a voxel.

2. **minor** - bands_gpu/src/bands_gpu/findk.py:181-234 (`BandEvaluator.solve`) with the existing lobpcg: an empty
   or too small parity subspace gives frequencies 0 that are reported as converged. Evidence (reviewer runs):
   `group_velocity(slab_cell(255), (1.2, 0, 0), 2, (1, 0, 0), "tm", parity="even", mirror_axis=2)` returns freqs
   [0, 0], vg [0, 0], and `BandEvaluator.solve` returns converged True (the 2-D "tm" field is always z-odd, so
   the projector is zero). A 1-D cell with 7 points and parity even or odd gives four bands at 0, converged True
   (the block of 8 is larger than the parity subspace; SVQB drops columns and the zero vectors have theta 0). The
   projector halves the space, so this occurs at twice the grid size of the no-parity case. find_k then gives
   NaN without a reason. Fix: raise a ValueError when the projected start block loses columns (rank below the
   block size) or for "tm"/"te" with mirror_axis 2 and the empty parity; or mark such solves as not converged.

3. **minor** - bands_gpu/src/bands_gpu/findk.py:100-112 (`_check_symmetric`): a false ValueError for a symmetric
   structure when a face is exactly on a subpixel sample. Evidence: a slab of thickness d in a 5 a cell, 25 points,
   sub 8: d = 0.325, 0.375, 0.425, 0.475, 0.525, 0.575, 0.625, 0.675 all give "parity: the structure is not
   symmetric" (the rounding of the sample coordinates puts one mirror sample inside and the other outside). The
   failure is safe (no wrong number), but the message is wrong and parity cannot be used for these dimensions.
   Fix: say in the message that a face on a sample can cause this and that another n or sub removes it, or make the
   sample coordinates exactly mirror-symmetric in `Cell.axes`.

4. **minor** - bands_gpu/src/bands_gpu/findk.py:276-277 (default `kmag_max = 1.01 * omega * n_max`): the bound
   is on |k|, not on kmag, so it is wrong when korig is not zero. Evidence: homogeneous n 1.5, omega 0.2,
   kdir (1, 0, 0), korig (-0.1, 0, 0): the root kmag 0.4 exists, the default kmag_max is 0.303, and find_k returns
   NaN, converged False. Fix: default kmag_max = 1.01 omega n_max + |k_cartesian(korig)| (or the positive root of
   |korig + t k_hat| = 1.01 omega n_max), and say so in the docstring.
