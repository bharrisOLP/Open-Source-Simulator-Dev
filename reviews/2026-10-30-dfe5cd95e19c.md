## Findings

Reference for the tidy3d line numbers: tidy3d 2.12.2 as locked in `meow_gpu/uv.lock`,
`tidy3d/components/mode/solver.py`.

1. **major** `meow_gpu/src/meow_gpu/meow_backend.py:98-105` (direction flip). The code flips a mode when
   `Re(P_z) < 0`, with no other test. tidy3d (solver.py:497-519) flips only when the power flow is reliable
   (`|Re P| > 1e2 * TOL_EIGS * |P|`), and else uses the passive rule `keff >= 0`. For evanescent modes of a lossless
   guide (`Re P` is rounding noise) the GPU sign is random, so the backend returns growing modes (`Im neff < 0`) that
   depend on the random seed. This is a silent wrong result in double precision whenever the requested window holds
   modes below cutoff (many modes, or a small domain). Repro (scratch script, double precision, no PML): Si width
   step 0.4 -> 0.7 um, 2 cells of 2 um, mesh x -0.5..0.5, y -0.3..0.52, dx 40 nm, 16 modes.
   - Raw neff of the wide cell: tidy3d `+1.9326j, +1.882j, ..., 0.1788±1.5935j`; GPU (seed 0)
     `-1.9326j, -0.7185j, +0.7475j, -0.934j, ..., -0.1788-1.5935j`.
   - After meow's post-processing, `|S21_00|` is 0.957019 (seed 0) and 0.960326 (seed 2), against 0.958574 for
     tidy3d: an error of about 2e-3 that changes with the seed. Kept modes with `Im neff < 0` exist only on the GPU
     path. The same occurs for a single cross-section (1.0 x 0.8 um domain, 16 modes, seeds 0, 1, 2).
   - Fix: copy the tidy3d rule (reliable test, then `keff < 0` fallback), and add a test with modes below cutoff in
     the window (compare neff signs and an S-matrix with `compute_modes_tidy3d`).

2. **minor** `meow_gpu/src/meow_gpu/fde/eigensolver.py:216,260` with `:282-283` (mixed precision). If the complex64
   stage uses all `max_iter` iterations, the complex128 stage gets `max_iter - lo.iterations = 0`, the loop does not
   run, and `return EigResult(..., it, ...)` raises `UnboundLocalError`. Repro:
   `GPUModeSolver(precision="mixed", max_iter=5).solve(problem, 4)`. With the default `max_iter=500` this needs a
   complex64 stage that never gets below `STALL_FLOOR` (very fine grids). Also, a slow complex64 stage leaves the
   polish with almost no iterations. Fix: initialize `it = 0` and give the polish its own iteration budget.

3. **minor** `meow_gpu/src/meow_gpu/fde/eigensolver.py:217-230` (missed eigenvalues with PML). The convergence test
   checks only the residuals of the selected Ritz pairs. It does not show that no eigenvalue nearer the target is
   missing. Repro: strip 0.45 x 0.22 um, domain 2.4 x 1.6 um, dx 40 nm, `num_pml=(12, 0)`, K = 6, double. tidy3d
   returns `1.71167+0.79220j` (|lambda - target| = 10.149); the GPU solver returns `converged=True` with
   `1.35506+0.01404j` (10.247) instead, also with `extra=16`. Two PML modes (10.149, 10.186) are missed. meow's
   `is_pml_mode` filter removes these modes, so the kept meow modes matched tidy3d for `num_pml` (12, 0), (8, 8) and
   (0, 10). No test solves eigenpairs with PML (only the operator test uses PML). Add one, and say in the docstring
   that the "nearest k" set is not guaranteed for complex (PML) spectra.

4. **minor** `meow_gpu/src/meow_gpu/meow_backend.py:29-31,82-89` (single-precision tolerance). The floor
   `10 * eps32 * |A| / |theta|` grows as 1/dx^2: about 1.2e-4 at 20 nm, 4.8e-4 at 10 nm, 1.9e-3 at 5 nm. There is
   no cap and no warning, and `SINGLE_FLOOR = 1e-3` also marks stalled solves as converged. Measured at 10 nm
   (0.5 um strip, 3 x 2 um, 6 modes): residual 3.9e-4 accepted; neff error 1.3e-6, but the eigenvector error
   (sine of the angle against tidy3d) is 4e-4 to 7e-4 for the near-degenerate modes 3 to 5. The README sentence
   "single-precision error of the S-parameters (about 2e-5)" comes from one 20 nm case and the fundamental mode
   only. State the grid dependence, and warn when the floor is above a limit.

5. **minor** Benchmarks against README (`meow_gpu/bench/bench_fde.py:88-102`, `meow_gpu/README.md` results).
   - "GPU single, cold" is the median of repeat runs after a discarded first run. It excludes the JIT compile and
     the 1-D eigenbasis setup (the `_BASES` cache hits on repeats). The tidy3d time includes all setup and its field
     and normalization post-processing; `gpu_modes` times only the eigen solve (no `fields()`, no flip, no meow
     post-processing). Call the column "cold start, compiled, setup cached", or time the full call.
   - `bench_fde.py` calls `davidson` with `tol=1e-5` (no floor) and `extra=4`. That is not the `GPUModeSolver`
     configuration that the README tells users to use (floored tolerance, `extra=8`).
   - "Warm" is a strip 5 nm wider, started from converged modes: a best case. The STATUS line "11.4x faster warm"
     compares it with a cold tidy3d solve.
   - `bench_fde.py` does not set `OMP_NUM_THREADS=1`, so "one core" depends on the shell of the run.
   - The row "3.0 um strip, 10 nm grid, 200k unknowns" needs a domain of 5 um (not the default `--w-dom 3.0`, where
     a 3.0 um "strip" fills the domain). Give the command line of each row. No logs are committed, so the reviewer
     could not check the numbers.
   - The 8-process tidy3d baseline scales only 1.55x on 8 cores (20.6 s -> 13.3 s). Worker spawn and imports
     (about 1.4 s for meow plus tidy3d on the reviewer's computer) are part of it. The "2.1x faster than 8 processes"
     claim depends on this harness; say so.

6. **minor** `meow_gpu/src/meow_gpu/fde/eigensolver.py:238-243,296-358` (`jd_correction`). It runs only when
   `inner_steps > 0`, which no default path and no test uses. It solves the GMRES least squares through the normal
   equations (squares the condition number; poor in complex64). Remove it or add a test.

7. **minor** Tests. `meow_gpu/tests/tidy3d_ref.py:26-32` uses tidy3d's own `create_d_matrices` and
   `create_s_matrices` (independent, and the random eps, non-uniform grid and PML cases make the stencil and PML-speed
   check meaningful), but the P Q assembly is a hand copy. The reviewer compared it with tidy3d solver.py:596-620
   (mu = 1): it is the same. `fields()` (`operator.py:142-156`) is not compared with tidy3d's E and H; only the
   transverse fields are checked through meow overlaps. The reviewer compared it by hand with solver.py:744-763
   (Hx, Hy = q_mat u / (i neff - keff), Hz = Dxf Ey - Dyf Ex, Ez from q_ep, H times -i/eta0): it is the same. Add a
   direct E, H test (all six components).

8. **minor** `meow_gpu/src/meow_gpu/meow_backend.py:10-11,117-122` and README "Not supported yet". The text says that
   off-diagonal permittivity falls back to tidy3d, but `_supported` does not test it. meow passes only diagonal
   indices, so there is no effect now; correct the text. Also `solve` sets the default target from the largest real
   eps (`:64`), and tidy3d uses the largest |eps| (solver.py:255-259); they differ for lossy and metal media.
