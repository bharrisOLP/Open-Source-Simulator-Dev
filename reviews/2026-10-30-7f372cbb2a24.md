1. minor - charge_gpu/src/charge_gpu/drift_diffusion.py:318-321 (the DEVICE_ERRORS comment), also README.md:11-14
   and :34-39. The catch is wider than "device errors". The comment says "Other errors (TypeError, ...) are
   programming errors and propagate", but some caught classes are also programming errors: ValueError includes the
   numpy broadcast error, RuntimeError includes NotImplementedError and RecursionError, ArithmeticError includes
   ZeroDivisionError. Evidence (probe on the GPU computer, junction n=200, 0.6 V, coupled.Solver.solve replaced):
   a numpy broadcast bug (np.ones(3) + np.ones(4)) gave linear_errors {"ValueError": 11}, converged True, 11
   RuntimeWarnings; a NotImplementedError gave {"NotImplementedError": 11}. A TypeError propagated, as claimed.
   The result is not wrong (each such step is the SuperLU reference step), a RuntimeWarning is given, and the
   continuation tests now assert `not s.linear_errors`, so a regression in the tested cases still fails the tests.
   But a user with an untested mesh gets the slow path with only a warning. Also: in jax 0.11.1 (the GPU
   environment) the class is jax.errors.JaxRuntimeError (MRO: RuntimeError); jaxlib.xla_extension.XlaRuntimeError
   does not exist any more. Fix: narrow DEVICE_ERRORS to (continuity.SpanError, jax.errors.JaxRuntimeError,
   MemoryError), or keep the width and say in the comment and the README that some programming errors (ValueError,
   NotImplementedError) also fall back with a warning; name JaxRuntimeError in the text.
